# service-template

A copy-paste starting point for a new Kimo Wallet backend microservice,
distilled from `apps/user-service` and `apps/wallet-service` — the two
existing reference implementations. It follows every rule in
`docs/CLAUDE.md` §5.4 (Go service layout, GORM-only, forward-only
migrations, structured logging) so a new service starts compliant instead
of needing a cleanup pass later.

**This template ships a fake "Widget" entity** (`internal/domain/widget.go`
et al.) as the smallest realistic example of the full stack — a create +
get-by-id flow through domain → service → repository → gRPC. Renaming
"Widget" to your real entity (step 3 below) is not optional polish.

## What's verified vs. what you still have to do

Everything except the gRPC layer builds and passes as-is, today, with no
placeholders:

- `internal/domain`, `internal/idgen`, `internal/config`,
  `internal/storage/postgres`, `internal/service` — real, tested code.
  `go build ./... && go test ./...` from this directory passes right now.
- `internal/storage/postgres/widget_repository_test.go` is a real Postgres
  integration test (same `*_TEST_DATABASE_URL`-gated pattern as the other
  two services) — it was run against a live throwaway Postgres database
  while building this template and passed; see `docs/agent-logs/2026-09-13.md`
  Entry 2 for the full verification record.

**`internal/grpcserver/widget_server.go` and `cmd/server/main.go` will not
build until you generate protobuf code for your service** — they import
`.../gen/widget/v1`, which doesn't exist until you've written a real
`.proto` and run `buf generate` (step 4 below). This isn't a template
shortcut: every real service in this repo has the exact same dependency —
a service's gRPC layer cannot exist before its contract does. Both files
*were* compiled and smoke-tested against real generated code (a temporary
proto, deleted afterward) before this template was committed, so the code
itself is proven correct — it's only missing its contract.

## Step-by-step: turning this into a real service

1. **Copy and rename the directory:**
   ```
   cp -r apps/service-template apps/<your-service>
   ```

2. **Rename the Go module and every import path.** From
   `apps/<your-service>`:
   ```
   sed -i '' 's/service-template/<your-service>/g' go.mod $(grep -rl "service-template" --include="*.go" .)
   ```
   (On Linux, drop the `''` after `-i`.) This fixes `go.mod`'s module line
   and every `github.com/jrmygp/kimo-wallet/apps/service-template/...`
   import.

3. **Rename the entity.** Find-and-replace `Widget`/`widget`/`widgets`
   with your real entity's name (`PascalCase`/`camelCase`/`snake_case`
   respectively) across:
   - `internal/domain/widget.go` → rename the file too
   - `internal/domain/widget_test.go`
   - `internal/storage/postgres/widget_repository.go` (+ `_test.go`)
   - `internal/service/widget_service.go` (+ `_test.go`)
   - `internal/grpcserver/widget_server.go`
   - `migrations/0001_create_widgets_table.sql` — rename the file and the
     `CREATE TABLE` statement. Add real columns; the template's `name`/
     `status` are placeholders, not a schema to preserve.
   - `cmd/server/main.go`'s `serviceName` const and every `widget*`
     identifier.

4. **Write your real `.proto` and generate code.** Move
   `proto-template/widget.proto` to
   `packages/contracts/<your-service>/v1/<your-service>.proto` (see its
   own header comment), rename its package/messages/`go_package` to
   match, then:
   - Add `buf.gen.<your-service>.yaml` at the repo root — copy
     `buf.gen.wallet-service.yaml` and change the two `out:` paths to
     `apps/<your-service>/gen`.
   - `buf generate --template buf.gen.<your-service>.yaml --path packages/contracts/<your-service>/v1/<your-service>.proto packages/contracts`
   - Delete `apps/<your-service>/proto-template/` — it was only a
     reference copy.

5. **Run `go mod tidy`** (needs network access) after renaming the module.
   `go.sum` is shipped and real (generated by an actual `go mod tidy` run
   while building this template, not hand-written), and stays valid after
   renaming your own module in step 2 — `go.sum` keys are on the
   *dependencies'* module paths, not yours. You only need to re-run it if
   you add a new dependency (e.g. `kafka-go`, if you copy in the event
   producer/consumer pieces mentioned below).

6. **Rename every `SERVICE_TEMPLATE_*` env var** in `.env.example` and
   `internal/config/config.go` to your service's own prefix (e.g.
   `WIDGET_SERVICE_*`), matching the existing convention
   (`USER_SERVICE_*`, `WALLET_SERVICE_*`).

7. **Give it its own Postgres.** Add a `<name>-db` service to the root
   `docker-compose.yml` (copy `wallet-db`'s block) and a matching
   `<NAME>_DB_*` block to the root `.env.example` — a service owns its
   data (`docs/CLAUDE.md` §4 rule 1), never a database shared with
   another service.

8. **Wire it into `api-gateway`** if the frontend needs to reach it: a
   second gRPC client connection in `api-gateway/cmd/server/main.go`
   (mirror how it already connects to `wallet-service`) plus a new/updated
   HTTP handler. The gateway never talks to a domain service's database
   directly, and never holds domain logic itself (`docs/CLAUDE.md` §4
   rule 2) — only protocol translation and aggregation.

9. **Rebuild and re-verify** from `apps/<your-service>`:
   ```
   go build ./... && go vet ./... && gofmt -l . && go test ./...
   ```
   Then run it against a real (throwaway or dev) Postgres database and
   confirm it boots, migrates, and listens — don't just trust a green
   build for a service that talks to a database (the same "verify, don't
   assume" principle `docs/CLAUDE.md` §5.6 applies to UI changes applies
   here too, just for a backend process instead of a browser).

## Deliberately not included

Kept out so the template stays a minimal, always-buildable core rather
than bundling every optional piece every service happens to need:

- **JWT minting** (`user-service`'s `internal/authtoken`) — only
  `user-service` issues tokens.
- **Kafka producer/consumer, the transactional outbox** (`user-service`'s
  `internal/outbox`/`internal/kafkaproducer`, `wallet-service`'s
  `internal/kafkaconsumer`/`internal/eventconsumer`) — copy from whichever
  of the two is the closer match (producing events vs. consuming them) if
  your service needs to participate in the event flow. Don't add a new
  Kafka topic or consumer group without reading `docs/CLAUDE.md` §3.6
  first (idempotent consumers, dead-lettering, no tight retry loops).
- **A dedicated `grpcserver` test file** — neither reference service tests
  that layer directly (it's thin: error-code mapping only), so the
  template doesn't either. Add one if your service's gRPC layer grows
  real logic.

## Money paths

If your new service will ever mutate a balance or write a ledger entry,
stop and read `docs/CLAUDE.md` §3 in full before writing that code — none
of it is encoded in this template. `wallet-service` does not yet mutate
balances either (only creates a zero-balance wallet today), so there's no
existing implementation in this repo to copy from for that part.
