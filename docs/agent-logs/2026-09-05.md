## Entry 3 — user-service publishes `user.created` (Phase 2 of 3: transactional outbox + Kafka producer)

- **time:** unknown
- **agent:** Claude Sonnet 5 (Claude Code)
- **task:** Phase 2 of 3 (Kafka infra → **user-service** → wallet-service). Make `user-service` publish a `user.created` event to Kafka after every successful registration, reliably — via the transactional outbox pattern, not a bare "publish after insert."
- **status:** completed
- **scope:** packages/contracts, apps/user-service
- **touches_money:** no

### What changed
- `packages/contracts/user/v1/events.proto` (new) — `UserCreated { string user_id; google.protobuf.Timestamp created_at; }`. Deliberately minimal: only what a consumer needs to provision a wallet, not User Service's profile fields (phone number, full name, ...) — publishing those would leak data ownership across the service boundary for no reason (`docs/CLAUDE.md` §4 rule 1). This is the wire contract per §1 rule 5 ("never invent a contract") — regenerated `apps/user-service/gen/user/v1/events.pb.go` via the same verified `buf generate` template used in earlier entries. `api-gateway` does not need this regenerated; it never touches this event.
- `apps/user-service/migrations/0003_create_outbox_events_table.sql` (new) — `outbox_events (id UUID PRIMARY KEY, event_type TEXT NOT NULL, payload JSONB NOT NULL, created_at TIMESTAMPTZ NOT NULL DEFAULT now(), published_at TIMESTAMPTZ)`, plus a partial index on `created_at WHERE published_at IS NULL` (the relay's only query shape). `id` is app-generated (`idgen.NewV4()`), matching `users.id`'s existing convention, not a DB-side default — kept consistent rather than introducing a second id-generation style.
- `apps/user-service/internal/domain/outbox.go` (new) — `domain.OutboxEvent{ID, EventType, Payload}`, the neutral shared type both the storage layer and the relay depend on (mirrors how `domain.User`/`domain.RegisterInput` already sit between `service` and `postgres` — deliberately not defined inside either layer, to avoid one importing the other).
- `apps/user-service/internal/storage/postgres/outbox_repository.go` (new) — `OutboxRepository.FetchUnpublished(ctx, limit)` / `.MarkPublished(ctx, id)`, plus `EventTypeUserCreated = "user.created"` (also doubles as the Kafka topic name — a deliberate 1:1 mapping).
- `apps/user-service/internal/storage/postgres/user_repository.go` — `Create` now wraps the user insert **and** a `user.created` outbox insert in one `db.Transaction(...)` — the transactional outbox pattern (`docs/CLAUDE.md` §3.4 rule 3 / §5.4): either both rows commit or neither does, so the event can never be silently lost even if the process dies immediately after. The pgErr unique-violation handling (phone number / KimoID collision) moved inside the transaction closure, functionally unchanged otherwise.
- `apps/user-service/internal/kafkaproducer/producer.go` (new) — thin wrapper around `segmentio/kafka-go`'s `Writer`. Chosen over `confluent-kafka-go` because it's pure Go (no `cgo`/`librdkafka` system dependency to install for local dev or Docker builds) — logged per `docs/CLAUDE.md` §4 rule 7, no Go stdlib Kafka client exists so an external dependency was unavoidable either way.
- `apps/user-service/internal/outbox/relay.go` (new) — `Relay.Run(ctx)` polls `FetchUnpublished` on a fixed 2s ticker (`outboxRelayInterval` in `main.go`), publishes each event (topic = its `event_type`, key = its `id`), and calls `MarkPublished` only after a successful publish. A failed publish is retried on the next tick — bounded by the ticker, never a tight loop (§3.6 rule 3); no dead-letter queue, because an unpublished row has nothing wrong with it the way a poison-pill *consumer* message would — it just needs Kafka reachable again, so indefinite timer-based retry is correct here, not a gap.
- `apps/user-service/internal/config/config.go` — added `KafkaBrokers []string` (`USER_SERVICE_KAFKA_BROKERS`, comma-separated, defaults to `localhost:9092`). Given a soft default rather than `DatabaseURL`/`JWTSecret`'s fail-fast treatment, since outbox publishing is designed to tolerate being down/delayed, not fatal to the service.
- `apps/user-service/cmd/server/main.go` — wires `kafkaproducer.New(cfg.KafkaBrokers)` and `postgres.NewOutboxRepository(db)` into `outbox.NewRelay(...)`, started as a goroutine (`go relay.Run(ctx)`) alongside the existing gRPC server; producer closed via `defer`.
- `.env.example` — no change needed here (this entry's new env var has a hardcoded default; `apps/user-service/.env`/`.env.example` weren't touched since `USER_SERVICE_KAFKA_BROKERS` isn't required — noting only because the day's earlier diff summary lists `.env.example` as modified, which was Entry 1's `KAFKA_PORT` addition, not this entry's).
- New tests: `TestUserRepository_Create` extended to assert a `user.created` outbox row exists (unpublished) after a successful `Create`; new `TestUserRepository_Create_DuplicatePhoneNumber` assertion that a **failed** `Create` leaves outbox_events empty — proving the transaction rolls back *both* inserts together, not just the user one. New `outbox_repository_test.go` (`FetchUnpublished`, its limit, `MarkPublished`). New `internal/outbox/relay_test.go` — pure unit tests against stub `Repository`/`Publisher` (publish-and-mark, publish-failure-leaves-unmarked, fetch-failure-does-not-panic), no DB or Kafka needed.

### Why
The event contract lives in `.proto` (not a hand-written Go/JSON struct) because `docs/CLAUDE.md` §1 rule 5 is explicit that cross-service data shapes — which this is, even though it's an event rather than an RPC — come from `.proto`, not from either side's head; Phase 3 (wallet-service) will generate its own consumer-side bindings from this same file rather than hand-writing a struct that has to be trusted to match.

The transactional outbox (write the event row in the same transaction as the effect, relay it out afterward) rather than "publish to Kafka right after the insert succeeds" is the whole point of this phase: a bare post-insert publish has a real gap — if the process dies between the commit and the publish call, the user exists forever with no wallet and no record that one was ever supposed to be created. Writing the event in the same transaction closes that gap: the event's existence is now exactly as durable as the user's.

None (no money, no balance, no ledger — this is user identity + a new outbox table). Contracts: added `events.proto`, additive only, no existing message changed.

### Why
Kept `retryBackoff` as a `Handler` struct field defaulted in `NewHandler`, rather than a package constant used directly in the sleep calls, specifically so tests could construct a `Handler{retryBackoff: 0}` and exercise the real bounded-retry-then-commit loop without actually sleeping — `docs/CLAUDE.md` §5.5 is explicit that tests never rely on sleeps, and the first draft of `handler_test.go` would have taken ~8 real seconds per test otherwise.

`CreateWallet` fetching and returning the *existing* wallet on `ErrWalletAlreadyExists`, rather than just swallowing the error, was a deliberate choice over the alternative (return the sentinel error, let the consumer's `process()` treat it as a non-error) — this way every caller of `CreateWallet` always gets back a real `domain.Wallet` on every success path, idempotent-no-op included, and nothing outside `WalletService` ever needs to know a collision happened at all.

### Do NOT do
- Don't add a `processed_events`/dedup table to wallet-service for the `user.created` consumer specifically — `wallets.user_id UNIQUE` already *is* the idempotency guard for this exact consumer (proven above), and a redundant dedup table would just be two sources of truth for the same fact. (A future consumer without a naturally-unique side effect might still need one — this isn't a blanket rule against ever having one, just against adding one *here* where it's redundant.)
- Don't "simplify" `WalletService.CreateWallet` by returning `domain.ErrWalletAlreadyExists` directly instead of fetching the existing wallet — that would push the idempotency-handling responsibility onto every caller instead of centralizing it once, and `eventconsumer.Handler.process()` specifically relies on `CreateWallet` never erroring on the redelivery path.
