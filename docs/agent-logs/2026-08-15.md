and concurrency, and (2) silent divergence between agents. §3 addresses the first; §2 the second.

Root `CLAUDE.md` is a one-line import rather than a copy so there is exactly one source of truth.

## Entry 2 — Formik + Yup form rules added to ruleset

- **time:** 11:35
- **agent:** Claude Opus 5 (Claude Code)
- **task:** Update the agent ruleset after the form-handling/validation stack changed to Formik + Yup
- **status:** completed
- **scope:** docs
- **touches_money:** no

### What changed
- `docs/CLAUDE.md` §5.2 — API-response validation now specifies Yup schemas (was "Zod or
  equivalent"), and requires reusing the same schemas as the forms so there is one validation
  library on the frontend.
- `docs/CLAUDE.md` §5.3 — new section "Forms & Validation (Formik + Yup — mandatory, no
  exceptions)": 6 general rules (no second form/validation library, schema per form, schema
  location + inferred types, wire via `validationSchema`, client validation is UX not security,
  a11y error binding) plus 7 money-form rules.
- `docs/CLAUDE.md` — old §5.3 Backend → §5.4, old §5.4 Testing → §5.5.
- `docs/CLAUDE.md` §5.5 — added a test requirement for Yup schemas on money forms (zero, negative,
  non-numeric, above balance, above max), tested directly rather than only through the form.
- `docs/CLAUDE.md` §9 — Definition of Done now rejects any form/validation library other than
  Formik + Yup.
- `docs/CLAUDE.md` §10 — Quick Reference gained a forms line.

### Why
`docs/guides/Kimo-Wallet-Architecture.md` §15 now lists Formik + Yup where the frontend stack
previously implied React Hook Form + Zod. The ruleset had one stale Zod reference, and — more
importantly — no forms guidance at all, even though every money movement in this product enters
through a form.

The money-form rules exist because Formik has three specific traps for a payment flow:

- `isSubmitting` looks like a duplicate-submit defence and is not one (it dies on remount and does
  nothing about network-level retries), so §5.3 rule 8 requires button-disable *and* idempotency key
  *and* server enforcement, and forbids arguing any one makes another redundant.
- Storing the idempotency key in Formik state means it re-mints on remount/retry — the exact
  double-disbursement bug §3 is written to prevent. Rule 9 puts the key outside form state,
  consistent with §3.7 rule 2.
- `resetForm()` on error destroys the intent, so the user's retry becomes a *second* payment
  rather than a retry of the first. Rule 10 forbids reset before a terminal server response.

Amount handling (rule 7) keeps strings in form state rather than `yup.number()`, because
`yup.number()` produces a JS float and §3.3 rule 4 rejects float money outright.

### Invariants affected
None directly — documentation only. Reinforces the §3.7 frontend money invariants by binding them
to the concrete Formik API surface.

### Verification
Docs only, no build applies. Verified with `grep -n "§5\|Zod" docs/CLAUDE.md` that the only
remaining Zod mention is the explicit prohibition in §5.3 rule 1, and that section numbering
5.1→5.5 is sequential with no dangling cross-references.

### Known gaps / TODO for the next agent
- Formik and Yup are **not yet installed** — `apps/web/package.json` currently has only next, react,
  react-dom. Whoever builds the first form adds them.
- The shared amount parse/format helper required by §5.3 rule 7 does not exist yet. Write it once
  (suggested `apps/web/lib/money.ts`), with tests, before the first money form — not inline in a
  component.
- `apps/web/features/transaction/types.ts` is still empty. When it is filled, amounts must be
  integer minor units, and the form's shape should be inferred from its Yup schema rather than
  declared twice.
- Consider an ESLint rule banning imports of `react-hook-form` / `zod` so §5.3 rule 1 is enforced
  mechanically rather than by trust.

### Do NOT do
- Do not "improve" the money form by switching to React Hook Form or adding Zod for resolvers.
  §5.3 rule 1 forbids it; raise it with the human instead.
- Do not use `yup.number()` for a rupiah amount. See §5.3 rule 7 and §3.3 rule 4.
- Do not move the idempotency key into Formik `initialValues` because it is "cleaner". It is not —
  it is the double-disbursement bug.

## Entry 3 — Change log switched to one file per day

- **time:** 11:45
- **agent:** Claude Opus 5 (Claude Code)
- **task:** Change the log convention so sessions on the same day append to a single day file instead of creating a new file per session
- **status:** completed
- **scope:** docs
- **touches_money:** no

### What changed
- `docs/CLAUDE.md` §2 — rewritten. §2.1 filename is now the date alone (`YYYY-MM-DD.md`), one file
  per day; §2.2 is a new hard append-only rule; §2.3 when; §2.4 day-file header; §2.5 entry
  template (metadata is now a list per entry, not YAML frontmatter, since a file holds many
  entries); §2.6 INDEX line is now one per *entry* and carries the entry number.
- `docs/CLAUDE.md` §0 step 3 — agents must now read today's day file in full before editing, since
  it is where same-day predecessors wrote.
- `docs/CLAUDE.md` §1 rule 8, §9 item 7, §10 quick reference — updated to the day-file convention.
- `docs/agent-logs/2026-08-15.md` — new. Merges the two session files that already existed for this
  date into Entry 1 and Entry 2, content preserved verbatim (frontmatter converted to the per-entry
  metadata list, `##` headings demoted to `###`). This entry is Entry 3.
- `docs/agent-logs/2026-08-15-agent-rules-bootstrap.md`, `2026-08-15-formik-yup-rules.md` — deleted
  after their full content was moved into `2026-08-15.md`. No log content was lost.
- `docs/agent-logs/_TEMPLATE.md` — rewritten: day header + entry block, with usage instructions.
- `docs/agent-logs/INDEX.md` — line format now includes the entry number and points at the day file.

### Why
One file per session fragments a day's work across several files, so an agent starting mid-day has
to open and correlate all of them to reconstruct what happened. A single day file makes the most
recent context one read, and makes "who else worked today" obvious.

The risk this introduces is that a shared file invites destructive edits — an agent "tidying",
consolidating, or overwriting the file it is appending to. §2.2 exists to close that off, and it
names the specific failure modes (reword, reorder, summarize, clean up, overwrite with Write)
rather than relying on "be careful". An outdated entry is deliberately kept: a superseded decision
still tells the next agent what was tried and why it changed.

Per-entry YAML frontmatter had to go, since YAML frontmatter is only valid once at the top of a
file. It is now a metadata list inside each entry, carrying the same fields plus a time.

None — documentation and log-format only. No source, contracts, or migrations touched.

## Entry 4 — Mandatory UI verification before reporting done

- **time:** 18:40
- **agent:** Claude Opus 5 (Claude Code)
- **task:** Add a rule requiring agents to verify UI changes render correctly before calling a task complete
- **status:** completed
- **scope:** docs
- **touches_money:** no

### What changed
- `docs/CLAUDE.md` §5.6 — new section "UI Verification — look at it before you call it done":
  5.6.1 what counts as evidence (screenshot > computed style > resolved-CSS repro) and what does
  not (a green build, "should work", any appearance you did not observe); 5.6.2 the honest-report
  path when browser tooling is unavailable; 5.6.3 six repo-specific build-clean CSS traps;
  5.6.4 driving interactive state before verifying.
- `docs/CLAUDE.md` §1 rule 10 — extended: no "done" on a UI change without seeing it rendered.
- `docs/CLAUDE.md` §9 — new Definition of Done item 8 (rendered verification, or an explicit
  statement that it was not possible); old item 8 renumbered to 9.
- `docs/CLAUDE.md` §10 — quick reference gained the AFTER-step UI check.

### Why
The user reported agents repeatedly declaring UI work complete when the change did nothing at all,
forcing the same task to be re-requested and re-derived from cold context — the expensive failure
mode this ruleset exists to prevent.

The root cause is that the existing Definition of Done was satisfiable without ever looking at the
UI: `tsc`, `eslint` and `next build` all verify that code *compiles*, and none of them can observe
that a class was overridden, resolved to nothing, or rendered at zero height. Every bug listed in
§5.6.3 was found in this repo **after** a completely clean build, which is the direct evidence that
build output is the wrong signal for visual work.

§5.6.2 is deliberate: browser tooling was genuinely unavailable earlier in this session (extension
not connected). Without an explicit honest-reporting path, a rule demanding verification would just
pressure agents into asserting appearances they never observed — which is worse than admitting the
gap. The rule is "see it, or say you didn't" — never "claim it either way".

### Invariants affected
None — documentation only. No source, contracts, or migrations touched.

### Verification
Docs only, no build applies. Confirmed section numbering with
`grep -n "^### 5\.\|^## " docs/CLAUDE.md`: 5.1→5.6 sequential, §6–§10 intact, no dangling
cross-references. §5.6.3's six traps are transcribed from bugs actually fixed in this session
(sheet height specificity, `min-h-full` height chain, missing border width, conflicting overflow,
missing `min-h-0`, Avatar `xl`/`2xl` with no CSS) — not invented examples.

### Known gaps / TODO for the next agent
- Still unenforced mechanically. A PR touching `apps/web/**/*.tsx` or `*.css` could be required to
  include a screenshot or an explicit "not visually verified" note in its log entry.
- No visual-regression tooling exists (Playwright screenshots, Storybook). Worth considering once
  the wallet screens stabilise — it would turn §5.6 from a discipline into a check.
- §5.6.3 is a living list. When you find another build-clean CSS trap in this repo, append it
  rather than fixing it silently.

### Do NOT do
- Do not treat `npm run build` output as evidence a visual change worked. It never is.
- Do not write "the border is now red" / "it now fills the height" unless you looked. If the
  browser tools are unavailable, say that plainly instead — §5.6.2 exists precisely for that case.
- Do not verify only the default render of a stateful component. Open the sheet, submit the form,
  scroll the list (§5.6.4).
