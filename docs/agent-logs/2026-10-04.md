### What changed
- Branch `feat/server-resolved-wallets` created from `master` (the user's own uncommitted work at the time came along unchanged). Not committed.

- `apps/api-gateway/internal/handler/transaction_handler.go` — request body is now `{idempotencyKey, receiverUserId, currency, amount}`. The sender is `claims.Subject` (Entry 12's "body sender must equal JWT subject" 403 is replaced by "the sender is the JWT subject"; the no-claims 403 stays). The HTTP response no longer includes `senderWalletId`/`receiverWalletId`.
- `apps/api-gateway/internal/handler/transaction_handler_test.go` (new — Entry 12 flagged this as missing) — sender comes from the JWT even when the body names another sender plus wallet ids; the response has no wallet ids; no claims → 403 without calling transaction-service; malformed JSON 400, InvalidArgument 400, NotFound 404, AlreadyExists 409.
- `apps/web/app/wallet/transfer/[userId]/page.tsx` (user's in-progress file) — removed `senderUserId` from the mutation payload and the now-unused `useAppSelector`/`userData`. The user had **already**, during this session, switched to `receiverUserId: data?.id`, removed the wallet ids, and moved the idempotency key into `useState`; those are theirs, not mine.
- `apps/web/features/transaction/schemas/transfer.schema.ts` (user's in-progress file) — removed `senderUserId` from `transferSchema`.

### Why
The user asked where receiver-wallet lookup belongs. The receiver's wallet is deliberately never exposed to other users (`GET /v1/user/{id}` returns `wallet: null` for anyone but the caller — `walletForOwnProfile`), and a wallet id from the browser is untrusted input. transaction-service already called wallet-service for both users (Entry 12) but only to *compare* against client-supplied ids. Making the lookup the source of truth removes the client from the question entirely, which is strictly stronger than Entry 12's mismatch check: there's no client wallet id left to mismatch.

Entry 12's "Do NOT do" says not to discard the `GetWalletByUserID` response. This entry doesn't discard it; it now *is* the value persisted. Entry 12's mismatch errors/tests are superseded, not reverted.

The contract change is breaking at the proto level (`buf breaking --against '.git#branch=master'` reports exactly the two deleted fields). Per `docs/CLAUDE.md` §4.4 that normally means a new version directory. The user explicitly chose `reserved` instead: the endpoint is new, and reserving the numbers and names prevents them being reused with a different meaning.

### Invariants affected
money / authorization: which wallet a transfer debits and credits is now decided only by transaction-service from authenticated user ids (sender from the JWT via the gateway; receiver user id from the client, existence-checked through wallet-service). Contract: `transaction.v1.CreateTransactionRequest` fields 3 and 5 removed and reserved. Idempotency, the ledger, settlement and the state machine are unchanged; wallet-service still settles from the wallet ids on the stored transaction / `transaction.created` event.

### §3.8 money-change checklist
- **Request arrives twice?** Unchanged: the same idempotency key hits the `(idempotency_key)` unique constraint in `TransactionRepository.Create` → `ErrIdempotencyConflict` → gRPC AlreadyExists → HTTP 409. Proven by `TestTransactionRepository_Create_DuplicateIdempotencyKey` (real Postgres, passed this session) and the new gateway 409 mapping test. Still not §3.2 rule 4-compliant (it should return the original result, not 409); pre-existing, see the `grpcserver` comment.
- **Concurrently with itself on the same wallet?** `TestTransactionRepository_Create_ConcurrentDuplicateIdempotencyKey` (real Postgres) passed. Wallet resolution is a read-only lookup with no lock needed; the authoritative balance check and row lock live in wallet-service's settlement (unchanged).
- **Process dies halfway?** The wallet lookups happen before any write; the transaction row and outbox event are still written in one DB transaction (unchanged), so a crash leaves either nothing or both.
- **Event delivered three times?** Not affected by this change (consumers unchanged; covered by Entry 8's redelivery tests).
- **Ledger still balanced?** No ledger code touched.
- **Test proving the duplicate is rejected?** Yes: the repository duplicate and concurrent-duplicate tests above (passed), plus the gateway AlreadyExists→409 test.

## Entry 2 — Fix the transfer response-shape mismatch in the web client

- **time:** 20:01
- **agent:** Claude Code (Opus 5.5)
- **task:** Fix the response-shape bug reported in Entry 1: the web client validated POST /v1/transaction's `data` as a flat transaction, but the gateway nests it under `data.transaction`
- **status:** completed
- **scope:** apps/web
- **touches_money:** yes (it's the client side of the money-transfer response; no request, key or amount handling changed)

### What changed
- `apps/web/features/transaction/schemas/transfer.schema.ts` — new `transferTransactionSchema` matching api-gateway's `createTransactionResponseBody` field for field (`id, idempotencyKey, senderUserId, receiverUserId, currency, amount (integer), status, createdAt`; no wallet ids), and its `TransferTransaction` type. `transferResponseSchema` is now `{ transaction: transferTransactionSchema.required() }`. The old flat schema, which spread `transferSchema.fields`, and the `TransferResponseData` type are gone (no other users).
- `apps/web/features/transaction/api/transfer.ts` — `transferFunds` now returns `Promise<TransferTransaction>` = `envelope.data.transaction`, the same unwrap convention as `searchUserById` returning `envelope.data.user`.

### Why
With the flat schema, `transferEnvelopeSchema.validate` threw on every **successful** 201. `transferFunds` then rethrew it as "Something went wrong", so the page's `onError` fired for a transfer that had already been created. That invites a retry, which 409s on the same key.

### Invariants affected
none on the server. Client-side, a created transfer is now reported as a success instead of an error.

### Verification
- Captured the gateway's **real** response body by running `TransactionHandler.CreateTransaction` through a throwaway test (`internal/handler/zz_dump_response_test.go`, written to the scratchpad and **deleted** right after; confirmed gone with `ls`). The body is `{"statusCode":201,"message":"transaction created successfully","data":{"transaction":{...}}}`.
- Validated that real JSON against the actual `lib/api-envelope.ts` + `transfer.schema.ts` files (`node --experimental-strip-types`): VALID, and `data.transaction` is parsed. The previous flat shape is now rejected (`data.transaction.createdAt is a required field`).
- `tsc --noEmit` clean; `npm run lint` → 0 errors, 1 pre-existing warning; `npm run build` → 9/9 pages.
- **Not run:** a live transfer against the running gateway (its local binary is still the pre-Entry-1 build, which also returns wallet ids; yup ignores unknown keys, so that would also validate).

### Known gaps / TODO for the next agent
Still open from the re-check reported to the user this session (not fixed, the user asked only for this one):
- **Form can't submit on a fresh load/refresh:** `receiverUserId: data?.id ?? ""` is a Formik **initial value**. Formik reads initial values once (`useRef`, `enableReinitialize` false), so it stays `""` unless the search result was already cached on first render. `transferSchema` then fails "receiverUserId is a required field" with no visible field and no message. Fix: read `data.id` in `onSubmit`, not form state.
- `transferSchema` is reused as the form schema: `amount: yup.number()` accepts `"0"`, `"-5000"`, `"1.5"` (sent as `1.5`, which int64 JSON decoding rejects → gateway "invalid JSON body"), and `"1e3"`, and shows yup's raw NaN message for an empty field (all verified by running the schema). §5.3.7 wants a string + digits-only + range + one integer-conversion helper.
- Idempotency key lives in Formik `initialValues` (§5.3.9), is minted on mount rather than at a review step, and is never rotated, so a second real transfer from the same page visit 409s.
- `note` initial value is `0` (renders "0") and is never sent (the contract has no note).
- No schema unit tests (§5.5); success/error only `console.log`, no "we're confirming" state (§3.7.5); no offline block (§3.7.6); the page's top comment (`page.tsx:18-24`) still claims "visual restyle only… no real endpoint yet".
- Server: a repeated key returns 409 instead of the original transaction (§3.2.4), pre-existing.

### Do NOT do
