### What changed

**Found via the scan (before any fix):**
- `migrations/0001_create_transactions_table.sql` had been renamed from the widget template but its *columns* were never updated — it still created `id, name, status, created_at` (the widget shape), not the sender/receiver/idempotency shape the Go code already expected. The `transactions` table did not exist in any real sense.
- Three different, mutually inconsistent sets of env var names for the same two variables across `internal/config/config.go` (`SERVICE_TEMPLATE_*`, leftover from the template), `.env` (`TRANSACTION_SERVICE_*`), and `.env.example` (`TRANSACTION_TEMPLATE_*`). The service could not start — `config.Load()` would immediately fail with `"SERVICE_TEMPLATE_DATABASE_URL is required"` even with a correctly-populated `.env`.
- `TransactionService.CreateTransaction`'s sender/receiver existence check was dead code: it checked `senderWallet.Wallet == nil` after a successful call, but `wallet-service`'s real `GetWalletByUserID` (checked its actual source, `apps/wallet-service/internal/grpcserver/wallet_server.go`) returns `status.Error(codes.NotFound, ...)` on a missing wallet — an error, never a success response with a nil `Wallet`. `domain.ErrSenderNotFound`/`ErrReceiverNotFound` could never actually fire; any nonexistent receiver fell through to a generic wrapped error.
- `domain.NewTransactionRequest` existed (right signature, matching the `NewRegisterInput`/`NewGetWalletByUserIDInput` convention used elsewhere in this repo) but did zero validation — just constructed and returned the struct unconditionally. It was also never called by anything; `grpcserver`/`transaction_server.go` built `domain.TransactionRequest{}` directly, bypassing it entirely.
- Idempotency-conflict detection in the repository checked for a Postgres constraint literally named `transactions_idempotency_key_key` (Postgres's auto-generated name for a single-column `UNIQUE(idempotency_key)`), but the GORM struct tags declared a *composite* index name (`idx_transactions_idempotency_key_sender`) on `(idempotency_key, sender_user_id)` — the two names didn't match anything that could ever exist together, so `domain.ErrIdempotencyConflict` could never actually trigger once a real migration existed.
- Root `.env` **and** `.env.example` had a copy-paste bug unrelated to any Go code: the "transaction-service's Postgres" block reused the `WALLET_DB_*` variable names instead of `TRANSACTION_DB_*` — duplicate keys for `WALLET_DB_NAME`/`WALLET_DB_PORT` in the same file, with the transaction values silently shadowing wallet-db's real ones for any tool that takes the last-defined value. `docker-compose.yml` already correctly declared a `transaction-db` service expecting `TRANSACTION_DB_*` — only the `.env` files were wrong. Found only because standing up `transaction-db` for live verification exposed it.
- Leftover unrenamed template artifacts: `Dockerfile` still built/named the binary `service-template`; `proto-template/widget.proto` was still present after the real proto already existed under `packages/contracts/transaction/v1/`; stale "TEMPLATE NOTE" comments and a "for widgets" package doc comment remained in `main.go`/`domain/transaction.go`/`service/transaction_service.go`.

**Fixes applied:**
- `packages/contracts/transaction/v1/transaction.proto` — rewritten from the old single-party shape (`user_id`/`wallet_id`/`kimo_id`) to match what `domain`/`service`/repository already expected: `idempotency_key`, `sender_user_id`/`sender_wallet_id`, `receiver_user_id`/`receiver_wallet_id`, `amount`, `currency`, `status` on `Transaction`; `CreateTransactionResponse` now wraps `Transaction transaction = 1` (matching `wallet.proto`'s `GetWalletByUserIDResponse{ Wallet wallet = 1; }` convention) instead of flat fields. Regenerated via `buf generate --template buf.gen.transaction-service.yaml --path packages/contracts/transaction/v1/transaction.proto packages/contracts`.
- `apps/transaction-service/migrations/0001_create_transactions_table.sql` — rewritten with the real columns (`idempotency_key`, `sender_user_id`, `sender_wallet_id`, `receiver_user_id`, `receiver_wallet_id`, `amount BIGINT CHECK (amount > 0)`, `currency`, `status DEFAULT 'PENDING'`, `failure_reason`, timestamps), and the actual unique constraint: `CONSTRAINT transactions_idempotency_key_sender_user_id_key UNIQUE (idempotency_key, sender_user_id)` — named to match what the repository checks for.
- `internal/storage/postgres/transaction_repository.go` — `uniqueIdempotencyKeyConstraint` updated to `"transactions_idempotency_key_sender_user_id_key"` (matching the migration exactly); `Status: "Pending"` → a `statusPending = "PENDING"` constant (uppercase, matching this codebase's status-string convention elsewhere).
- `internal/config/config.go` — rewritten to read `TRANSACTION_SERVICE_DATABASE_URL`/`TRANSACTION_SERVICE_GRPC_PORT` (matching `.env`); dropped the dead, already-commented-out `UserServiceAddr` field (transaction-service validates existence via `wallet-service` only — see Why).
- `cmd/server/main.go` — removed the commented-out user-service connection block (`docs/CLAUDE.md` §5.1: no commented-out code) and the now-satisfied "TEMPLATE NOTE"; added a comment explaining *why* there's no user-service connection at all.
- `internal/domain/transaction.go` — `NewTransactionRequest` now actually validates: idempotency key non-empty, sender/receiver user/wallet ids UUID-shaped, sender ≠ receiver, amount > 0, currency non-empty — each with its own new sentinel error (`ErrInvalidIdempotencyKey`, `ErrInvalidID`, `ErrSenderIsReceiver`, `ErrInvalidAmount`, `ErrInvalidCurrency`). Removed the stale file-header "TEMPLATE NOTE" comment.
- `internal/service/transaction_service.go` — `CreateTransaction` now calls `domain.NewTransactionRequest(...)` first (wiring the validation in for real) and checks `status.Code(err) == codes.NotFound` on the wallet lookup's *error* to translate to `ErrSenderNotFound`/`ErrReceiverNotFound`, instead of the unreachable nil-check. Fixed the stale "for widgets" package doc comment.
- `internal/grpcserver/transaction_server.go` — `toProtoTransaction` now maps `IdempotencyKey` and `Status` into the response (previously dropped silently); the error switch now actually maps the new sentinel errors (`InvalidArgument` for the five validation errors, `NotFound` for sender/receiver-not-found, `AlreadyExists` for an idempotency conflict) instead of everything falling through to a blanket `Internal`.
- Root `.env` / `.env.example` — transaction-service's Postgres block renamed from `WALLET_DB_*` to `TRANSACTION_DB_*`, resolving the duplicate-key collision with wallet-db's real config.
- Cleanup: `Dockerfile` binary name `service-template` → `transaction-service`; deleted `apps/transaction-service/proto-template/` (the real proto now lives under `packages/contracts/`).

### Why

The `AlreadyExists` mapping for `ErrIdempotencyConflict` is a **conservative placeholder**, flagged in a code comment, not the fully-correct behavior: `docs/CLAUDE.md` §3.2 rule 4 says a repeated key should return the *original* transaction's result, not an error — that requires `TransactionRepository` to have a `GetByIdempotencyKey`-style lookup, which doesn't exist yet. Rejecting loudly is safer than the alternative bug class (silently creating a duplicate), but it isn't the end state.

Skipping a `user-service` connection entirely (rather than wiring the one the user had already half-connected) matches this session's earlier discussion with the user: a wallet can only exist for a user that was actually created (via `wallet-service`'s own `user.created` Kafka consumer), so a successful `GetWalletByUserID` already proves the user exists — a second round-trip to `user-service.GetUserByID` would be redundant, and `GetUserByID` is keyed by KimoID anyway, not the internal `user_id` this request already carries.

### Invariants affected
None directly (no ledger, no balance mutation). Existence-check correctness and idempotency-conflict detection are exactly the kind of thing §3's money-safety rules care about, even though this service doesn't move money yet — fixing them now means the eventual balance-moving logic builds on a foundation that already rejects duplicates and validates its inputs, rather than inheriting silent gaps.
