## Entry 1 — Fix unreachable auto-logout condition; add real route protection

- **time:** unknown
- **agent:** Claude Sonnet 5 (Claude Code)
- **task:** The user had added `if (msUntilExpiry <= 0 || !user?.id) { logout(); return; }` to `useAutoLogout` themselves, trying to make it kick a user with no session to the login page, but reported it "doesn't seem to redirect user to login page."
- **status:** completed
- **scope:** apps/web
- **touches_money:** no

### What changed
- `apps/web/features/auth/hooks/use-auto-logout.ts`:
  - **Root cause of the reported bug**: the function had an early `if (!user) return;` a few lines above the user's added condition. Since `state.user.user` is either `null` or a full profile object with a required `id` (see `user-slice.ts` / `userResponseSchema`), `!user?.id` could only ever be `true` in a state the early return had already intercepted — the condition was unreachable dead code, hence "nothing happens."
  - Fixing just that one line wasn't enough on its own: `useAutoLogout` is called by `AuthWatcher`, which is mounted once at the root layout (`app/layout.tsx`) and therefore runs on **every** route, including the public ones (`/`, `/auth/login`, `/auth/register`). Naively redirecting whenever `!user` would create a redirect loop against the login page itself and forcibly boot users off the registration form mid-signup, where having no user yet is completely normal.
  - Added a `PUBLIC_PATHS` set (`/`, `/auth/login`, `/auth/register`) and `usePathname()`; the "no session" branch now only calls `logout()` (which redirects to `/auth/login`) when the current route isn't in that set. Applied the same public-path guard to the pre-existing "no token in localStorage" branch for consistency (previously that branch just silently returned without logging out — a smaller pre-existing gap, not something this session was asked to touch, but the same one-line fix pattern applies cleanly).
  - **Found and fixed a second latent bug while implementing this**, not something the user reported: `apps/web/providers/redux-provider.tsx`'s `PersistGate` uses `loading={null}`, so it renders children (including `AuthWatcher`) immediately rather than blocking until `redux-persist` finishes rehydrating `user` from `localStorage`. On every fresh page load/refresh, `state.user.user` therefore starts as `null` for a brief moment — even for an already-logged-in visitor — until rehydration catches up a tick later. Adding the public-path-aware redirect without accounting for this would have flash-redirected every logged-in user on every page refresh. Fixed by reading `state._persist?.rehydrated` (exposed automatically since `persistReducer` wraps the whole root reducer in `lib/store/store.ts`, not per-slice) and doing nothing at all in the effect until it's `true`.
  - Updated the hook's doc comment to describe both of its jobs (proactive expiry logout + route guarding for the unauthenticated case) and the rehydration-gate reasoning, matching this file's existing high comment density.

### Why
The user's own framing ("kick user if userSelected is empty") is a legitimate second responsibility for this hook to have, given this app has no middleware-based route protection at all (no `middleware.ts`, confirmed by search) — `useAutoLogout`/`AuthWatcher` is the only mechanism enforcing auth on protected routes today. Rather than bolt a second, separate guard hook onto the codebase, this extends the existing single global mechanism, consistent with `docs/CLAUDE.md` §5.1 ("match the surrounding code" / small, single-purpose changes) — one mechanism for "you shouldn't be here without a session," whether that's because your token just expired or because you never had one.

The rehydration check is the one piece not asked for, but necessary: without it the fix would have been *worse* than the original unreachable-condition bug, actively logging out real users on refresh instead of just not doing anything.

### Invariants affected
None — no balance mutation, no ledger. Auth/route-access behavior changed (this is the first real enforcement that unauthenticated users can't view protected pages), but the underlying JWT/session mechanics are untouched.

### Verification
- `npx tsc --noEmit` — clean (also confirms `state._persist.rehydrated` is properly typed off `RootState`).
- `npm run lint` — 0 errors (1 pre-existing `react-hooks/exhaustive-deps` warning on `app/auth/login/page.tsx`, unrelated to this file, untouched by this change).
- `npm run build` (`next build`) — compiles successfully, all routes generated.
- **Full live browser verification** against the real running stack (dev server on :3000, api-gateway on :8080):
  1. Cleared `localStorage`, navigated directly to `/home` unauthenticated → redirected to `/auth/login`, page rendered correctly (no blank screen, no loop).
  2. Navigated directly to `/auth/register` unauthenticated → stayed on `/auth/register` (confirms `PUBLIC_PATHS` correctly excludes the auth pages from the guard).
  3. Registered a real user via `curl` (`Guard Test User`, `+6281355566677`), logged in through the actual UI, landed on `/home`, then did a **full page reload** on `/home` → stayed on `/home` with the correct user's data still showing (confirms the rehydration gate prevents the flash-redirect regression this fix could otherwise have introduced).

### Known gaps / TODO for the next agent
- `/home`'s balance display reads `state.user.balance`, which nothing currently populates (`setBalance` is never dispatched anywhere) — shows `"undefined undefined"` today. Noticed live during verification; pre-existing and unrelated to this fix (flagged previously in 2026-09-06's Entry 4 as a hardcoded-balance gap; still unwired, out of scope here).
- `PUBLIC_PATHS` is a flat set of exact paths. If a new public route is ever added (e.g. a marketing page, a password-reset flow), it must be added here too, or `AuthWatcher` will redirect visitors away from it. There's no wildcard/prefix matching — intentionally simple for the three routes that exist today, but worth a comment/reminder for whoever adds the next public route.
- The "user exists but no token" edge case's `logout()` behavior is now applied consistently with the "no user at all" case, but the scenario itself (redux-persist has a stale user while localStorage's separate `token` key is gone or was cleared, e.g. via devtools) is still not covered by any automated test — only manually reasoned about.

### Do NOT do
- Don't remove the `!rehydrated` early-return thinking it's unnecessary boilerplate — without it, this hook flash-redirects every already-logged-in user to `/auth/login` on every single page refresh, because `PersistGate`'s `loading={null}` (redux-provider.tsx) means `user` is briefly `null` before rehydration completes even when a valid session exists.
- Don't add a new public/auth page without adding its path to `PUBLIC_PATHS` — otherwise `AuthWatcher`, mounted globally at the root layout, will immediately bounce any unauthenticated visitor off it.

## Entry 2 — New `apps/service-template` for bootstrapping future backend services

- **time:** unknown
- **agent:** Claude Sonnet 5 (Claude Code)
- **task:** "make a template backend folder using my current services, so when i want to make a new service i can just copy the template folder" — a reusable skeleton distilled from `apps/user-service` and `apps/wallet-service`.
- **status:** completed
- **scope:** apps/service-template (new)
- **touches_money:** no

### What changed
- New `apps/service-template/` — a full Go service skeleton around a placeholder "Widget" entity (create + get-by-id), following the exact layout/conventions `docs/CLAUDE.md` §5.4 requires: `cmd/server/main.go`, `internal/config`, `internal/domain`, `internal/service`, `internal/storage/postgres` (GORM, `TranslateError: true`, silenced default logger, never `AutoMigrate`), `internal/grpcserver`, `internal/idgen`, forward-only embedded `migrations/`, `.env.example`, `Dockerfile`.
- `internal/domain/widget.go` (+ `_test.go`) — sentinel errors, a UUID-shape validator, and `NewCreateWidgetInput`/`NewGetWidgetByIDInput` mirroring `user-service`'s `NewRegisterInput`/wallet-service's `NewGetWalletByUserIDInput` pattern.
- `internal/storage/postgres/widget_repository.go` (+ `_test.go`) — GORM row-mapping struct kept separate from the domain type (same convention as `userModel`/`walletModel`); the test file is a real Postgres integration test gated behind `SERVICE_TEMPLATE_TEST_DATABASE_URL`, same skip-not-fail pattern as the two reference services.
- `internal/service/widget_service.go` (+ `_test.go`) — stub-based unit tests, same pattern as `wallet_service_test.go`.
- `internal/grpcserver/widget_server.go`, `cmd/server/main.go` — gRPC server + boot/shutdown wiring (config → `postgres.Open` → `Migrate` → repo → service → grpcserver → `grpc.NewServer` + `GracefulStop` on `ctx.Done()`), matching `wallet-service`'s `main.go` (the cleaner of the two references — no outbox/Kafka mixed in).
- `apps/service-template/proto-template/widget.proto` — a reference `.proto` to copy into `packages/contracts/<service>/v1/` when bootstrapping a real service.
- `apps/service-template/README.md` — the actual deliverable for "so I can just copy the folder": a numbered checklist (copy → rename module/imports → rename entity → write proto + `buf generate` → `go mod tidy` → rename env vars → add its own Postgres to `docker-compose.yml` → wire into `api-gateway` if needed → rebuild and re-verify), plus what's deliberately left out (JWT minting, Kafka producer/consumer/outbox, a `grpcserver` test) and where to copy each from if needed, plus a pointer to `docs/CLAUDE.md` §3 for any service that will ever touch money.
- Deliberately **excluded** from the template: JWT minting (`user-service`-only), Kafka producer/consumer + the transactional outbox (present in one or both reference services but not universal to every future service), and a `grpcserver`-layer test file (neither reference service has one either — that layer is thin).

### Why
Built directly off the two real, currently-deployed services rather than a generic Go-service tutorial skeleton, so copying it starts a new service already compliant with this repo's actual rules (GORM-only, forward-only migrations, structured JSON logs, `internal/domain` free of ORM tags) instead of needing a conformance pass afterward. Kafka/outbox/JWT were deliberately left out rather than bundled in "just in case" — not every future service will publish or consume events or mint tokens, and `docs/CLAUDE.md` §4 rule 6 already discourages adding infrastructure a service doesn't need; the README instead documents exactly which existing file to copy from if a new service does need one of these.

### Invariants affected
None — no money, no ledger, no auth. New template code only; no existing service's behavior changed.

### Verification
This is the one place in the template where "go build succeeded" alone would not have been honest, since the gRPC layer (`internal/grpcserver`, `cmd/server/main.go`) references generated protobuf code that doesn't exist until a real `.proto` is written and `buf generate` is run — true for this template and for any brand-new real service alike. Verified in full rather than assumed:
- `go build ./... && go vet ./... && gofmt -l .` for every layer that doesn't depend on generated code (`internal/domain`, `internal/idgen`, `internal/config`, `internal/storage/postgres`, `internal/service`) — clean.
- `go test ./...` for those same layers — all pass, including `TestWidgetRepository_*` run twice: once confirming the expected `SKIP` (no `SERVICE_TEMPLATE_TEST_DATABASE_URL` set) and once for real, against a throwaway Postgres database created inside the already-running `kimo-wallet-user-db-1` container (`CREATE DATABASE service_template_test`), which the migration runner correctly created the `widgets` table in — all 3 tests passed, then the throwaway database was dropped.
- **The gRPC layer specifically**: temporarily added `packages/contracts/widget/v1/widget.proto` and a root `buf.gen.service-template.yaml`, ran the real `buf generate`, and confirmed `internal/grpcserver/widget_server.go` + `cmd/server/main.go` compile and vet clean against the generated code, and `go test ./...` for the whole module still passes. Went one step further and actually booted the compiled binary (`go run cmd/server/main.go`) against a second throwaway database (`service_template_smoke`), confirmed via its structured log output that migrations applied and the gRPC server started listening, confirmed the `widgets` table's real schema via `psql \d widgets`, then killed the process and dropped the database. Afterward, deleted the temporary proto, the temporary root `buf.gen.service-template.yaml`, and `apps/service-template/gen/` (generated code is never committed — `docs/CLAUDE.md` §5.4 / repo `.gitignore`'s `apps/*/gen/`), leaving `packages/contracts/` and the root `buf.gen.*.yaml` set exactly as they were before — no permanent "widget" entry was added to the real shared contracts registry.
- Confirmed post-cleanup that `go build ./internal/grpcserver/...` and `cmd/server` now fail with a clear "no required module provides package .../gen/widget/v1" error, matching exactly what the README tells the next user to expect at that stage — not a stale claim.
- `git status` after cleanup showed only `apps/service-template/` as new — no leftover diff in `packages/contracts/` or the root `buf.gen.*.yaml` files.

### Known gaps / TODO for the next agent
- The template's `go.sum` is real (generated by an actual `go mod tidy` while building this) and stays valid after renaming the module in `go.mod` — `go.sum` keys the *dependency* modules, not this one's own name — but it will need `go mod tidy` re-run if a copied service adds a new dependency (e.g. `kafka-go`, if the outbox/consumer pieces are copied in per the README).
- No CI/lint step in this repo currently enforces "does `apps/service-template` still build" over time — if `user-service`/`wallet-service`'s shared patterns (e.g. `postgres.Open`'s GORM config) change, this template's copies won't automatically follow. Worth a periodic manual diff against the two reference services if they drift significantly.
- `transaction-service` (`apps/transaction-service`) exists as an empty directory in this repo already — this template was not used to seed it, since that wasn't part of the request; flagging in case the next agent wonders whether it should have been.

### Do NOT do
- Don't add Kafka, an outbox, or JWT minting to this template "for completeness" — see Why above. A service that needs one should copy it from whichever real service is the closer match, deliberately, not inherit it by default.
- Don't commit a `gen/` directory under `apps/service-template` — it must stay generated-only, exactly like every other service's `gen/` (gitignored, rule already in `docs/CLAUDE.md` §5.4).
- Don't "fix" the fact that `cmd/server/main.go`/`internal/grpcserver` don't build out of the box — that's not a bug, it's the correct, honestly-documented state until a real `.proto` exists for whatever service is copied from this template.
