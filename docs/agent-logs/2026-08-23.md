## Entry 1 — Wire login page to the login endpoint; found and fixed a real CORS gap; added TanStack Query per mid-session request

- **time:** 10:02
- **agent:** Claude Sonnet 5 (Claude Code)
- **task:** "connect my login page in web service with my login endpoint" — then, mid-task,
  "i forgot to tell you i want to use tanstack query for useFetch and useMutation please."

- **scope:** apps/web, apps/api-gateway
- **touches_money:** no

### What changed
- **apps/web** (the user had already started some of this independently — `lib/axios.ts`,
  `features/auth/schemas/login.schema.ts` existed before this session; noted below where I
  built on top of it vs. added new):
  - `lib/api-envelope.ts` — new. `apiEnvelopeSchema(dataSchema)`, a Yup schema factory for
    the gateway's `{statusCode, message, data}` envelope. Exists because `lib/axios.ts`'s
    response interceptor unwraps axios's own `.data` wrapper at runtime, but axios's
    TypeScript types don't reflect that interceptor — the resolved value is typed
    `AxiosResponse<T>` while actually being the envelope itself. Per `docs/CLAUDE.md` §5.2
    ("a network response is not a typed object just because you annotated it"), the fix is
    to treat the resolved value as `unknown` and validate/cast with Yup, not trust the cast.
  - `features/auth/schemas/login-response.schema.ts` — new. Yup schema + inferred
    `LoginResponseData` type for the login endpoint's `data` payload
    (`{user: {...}, accessToken}`).
  - `features/auth/api/login.ts` — new. `loginUser(phoneNumber)`: calls
    `POST /v1/auth/login`, validates the response against
    `apiEnvelopeSchema(loginResponseSchema)`, and on any failure throws a plain `Error`
    with a safe message — either the gateway's own curated message (validation error,
    not-found — these are deliberately safe user-facing strings on the backend, see
    2026-08-21/22 entries) or a generic connectivity message if the gateway never
    responded at all.
  - `features/auth/schemas/login.schema.ts` — tightened (was `.required()` only): `number`
    now also requires digits-only and a 5–13 length range via `.matches()`/`.min()`/`.max()`.
    Added an exported `LoginFormValues` inferred type (was missing, per §5.3 rule 3 every
    schema should export its inferred type alongside it).
  - `providers/query-provider.tsx` — new. `QueryProvider`, a client component wrapping
    `QueryClientProvider` with a `useState`-created `QueryClient` (one instance per browser
    session, not module-scope-shared). Wired into `app/layout.tsx` around `{children}`.
  - `features/auth/hooks/use-login-mutation.ts` — new, **added after the mid-session
    TanStack Query request**. `useLoginMutation()` wraps `loginUser` in `useMutation`.
    Login is a mutation (side effect: issues a session token), not a query, hence
    `useMutation` not `useQuery`/`useFetch` — no read-only endpoint exists yet for the
    latter pattern to apply to, so it wasn't built speculatively.
  - `app/auth/login/page.tsx` — was previously just `router.push("/home")` with no API
    call at all. Rewritten to: combine `formik.values.country` (ISO alpha-2, from
    `CountryCodeSelect`) + `values.number` into an E.164 string via `country-codes-list`'s
    `countryCallingCode` lookup, call `loginMutation.mutate(phoneNumber, {onSuccess...})`,
    store the returned `accessToken` in `localStorage` under `"token"` (matching what
    `lib/axios.ts`'s request interceptor already reads), then navigate to `/home`. Submit
    button disabled via `loginMutation.isPending` (not Formik's `isSubmitting` — `onSubmit`
    is now synchronous, calling `.mutate()` fire-and-forget, so Formik's own submitting
    state doesn't apply; TanStack Query's own pending/error state replaced my first-draft
    hand-rolled `apiError` `useState` + manual `setSubmitting` juggling entirely). Errors
    surfaced via `loginMutation.error.message` in a `role="alert"` paragraph.
- **apps/api-gateway** — real bug found while verifying the above, not part of the original
  ask but blocking it entirely:
  - `internal/middleware/cors.go` — new. `CORS(allowedOrigin)` middleware: sets
    `Access-Control-Allow-{Origin,Methods,Headers}` on every response and short-circuits
    `OPTIONS` requests with `204` before they reach the router. Has to wrap the *whole*
    server (`middleware.CORS(origin)(router)` in `main.go`), not a single route — the
    reason is structural: `http.ServeMux`'s method-specific patterns (`"POST
    /v1/auth/login"`) simply don't match an `OPTIONS` request to that path at all, so an
    unwrapped router 405s any preflight regardless of which route it's for.
  - `internal/config/config.go` — added `CORS_ALLOWED_ORIGIN` (defaults to
    `http://localhost:3000` — a safe default: worst case if forgotten in a real deploy is
    that real traffic gets rejected, not that an overly permissive origin gets allowed).
  - `internal/middleware/cors_test.go` — new. Two cases: an `OPTIONS` preflight is
    answered directly with `204` + correct headers and never reaches `next`; a real request
    gets the same headers and does reach `next`.
  - `internal/handler/user_handler_test.go` — fixed a **pre-existing, unrelated test
    failure** found while re-running the suite after the CORS change: `GetUserByID`'s
    response shape had been changed (by the user, concurrently, outside this specific
    exchange — nests under `{"user": {...}}} now instead of returning the user object
    directly, plus a new empty-id `400` guard) since the test was last written. Updated
    the success-case assertions to match the new `userData{User: userResponseBody}` shape
    and added `TestUserHandler_GetUserByID_MissingID` covering the new guard. This was a
    stale test catching up to a real, deliberate code change — not a regression I caused.

### Why
**The CORS bug is why "connect login page to login endpoint" didn't just work on the first
try.** Diagnosed by reproducing in a real browser (not curl, which bypasses CORS entirely
and made the endpoint look fine when tested directly): `read_network_requests` showed the
browser sending `OPTIONS /v1/auth/login` and getting `405`, which blocks the real `POST`
from the browser's perspective even though curl proved the POST handler itself was correct
all along. This was already flagged as a known gap in the 2026-08-21 Entry 4 log ("No CORS
handling... When that wiring happens, CORS headers... will be needed") — this is that
wiring happening, so it was the right time to fix it, not scope creep.

**TanStack Query added mid-session, not from the start** — the user's message arrived
after the initial axios-based implementation was already built and being verified live in
the browser. Rather than discard that work, the axios call (`loginUser`) was kept as the
`mutationFn` and TanStack Query was layered on top via `useMutation` — this is the correct
division of responsibility (axios/Yup handle the HTTP call and response validation,
TanStack Query handles request lifecycle/loading/error state for the UI), not a
redundant/competing abstraction.

### Invariants affected
None — Login is a read lookup, not a financial mutation; CORS and TanStack Query changes
are transport/UX concerns, not business logic.

### Known gaps / TODO for the next agent
- **CORS allows exactly one origin, from an env var with a single default.** Fine for this
  project (one frontend); if a second consumer origin is ever needed, `CORS(allowedOrigin
  string)` needs to become a real allowlist, not a copy-paste of the single-string version.
- **No register page/flow wired to the frontend yet** — this session's login flow requires
  a user to already exist; the test user was created via a direct `curl` to the gateway,
  not through any UI. `features/auth/api/register.ts` + a `useRegisterMutation` following
  the exact same pattern established here would be the natural next piece, and
  `lib/api-envelope.ts` / the `loginResponseSchema` pattern are already reusable for it.
- **`GetUserByID`'s authorization gap from the 2026-08-22 exchange is still open** — any
  authenticated user can still fetch any other user's record by id. Not addressed in this
  entry; still flagged as a TODO comment in `user_handler.go` itself.
- The `apiError`/manual-`isSubmitting` pattern from this session's first draft is now
  superseded by the TanStack Query pattern (`mutation.isPending`/`mutation.error`) — if a
  future form is built by copying the *old* login page instead of the current one, it'll
  reintroduce the pattern this session moved away from. Copy the current version.

### Do NOT do
- Do not "simplify" `internal/middleware/cors.go` by moving the OPTIONS short-circuit
  into an existing route on the mux, or by applying it per-route instead of wrapping the
  whole server — `http.ServeMux`'s method-specific patterns don't match `OPTIONS` at all,
  so a per-route application would silently stop working for preflights to that route.
- Do not assume a `curl`-verified endpoint works from the browser — CORS is enforced by
  the browser, not the server in a way curl reproduces. This was the entire reason the
  original "it should just work" attempt didn't; verify browser-origin calls with an
  actual browser (or at minimum an `Origin` header on curl, as done here), not curl alone.
- Do not reintroduce a second, hand-rolled loading/error-state pattern for a new mutation
  now that `useMutation` exists in this codebase — follow `use-login-mutation.ts`'s shape
  (thin wrapper around an already-Yup-validated API function) rather than inventing a new
  convention per feature.

## Entry 2 — Redux + redux-persist for logged-in user data

- **time:** 10:14
- **agent:** Claude Sonnet 5 (Claude Code)
- **task:** "now lets put the user data in redux and persist it using redux persist."
- **status:** completed
- **scope:** apps/web
- **touches_money:** no

### What changed
- Added `@reduxjs/toolkit`, `react-redux`, `redux-persist` (explicit user request, new
  dependencies — architecture doc doesn't mention Redux specifically, but the user asked
  by name so this isn't a judgment call to flag).
- `features/auth/store/user-slice.ts` — new. `userSlice` with `setUser`/`clearUser`
  reducers, state `{ user: UserProfile | null }`. `UserProfile` is `LoginResponseData["user"]`
  (imported from the schema added in Entry 1), not a hand-redeclared interface — same
  "infer, don't duplicate" reasoning `docs/CLAUDE.md` §5.3 applies to form schemas, applied
  here to keep the slice's shape from drifting out of sync with what the API actually
  returns. Lives under `features/auth/` (not `lib/`) since it's auth/user-domain state,
  matching the existing feature-first split (`features/auth/api/`, `.../schemas/`,
  `.../hooks/` are already organized this way).
- `lib/store/store.ts` — new. `combineReducers({ user: userReducer })` wrapped in
  `persistReducer` (key `"kimo-root"`, `redux-persist/lib/storage` = localStorage,
  **explicit `whitelist: ["user"]`** — persistence is opt-in per slice, not "persist
  everything by default," so a future non-persistable slice (e.g. transient UI state)
  doesn't get silently written to localStorage just by existing in the store).
  `configureStore` with `serializableCheck.ignoredActions` set to redux-persist's own
  `FLUSH/REHYDRATE/PAUSE/PERSIST/PURGE/REGISTER` action types — without this, RTK's
  default middleware logs a serializability warning for every one of them, every load;
  verified this actually works (see Verification) rather than assumed from memory.
  Exports `store`, `persistor`, and `RootState`/`AppDispatch` types.
- `lib/store/hooks.ts` — new. `useAppDispatch`/`useAppSelector` via react-redux 9's
  `useDispatch.withTypes<AppDispatch>()` / `useSelector.withTypes<RootState>()` — verified
  this API exists in the installed `react-redux@9.3.0`'s own `.d.ts` (its JSDoc examples
  literally show this exact pattern) before using it, since this replaces the older
  `TypedUseSelectorHook` pattern from react-redux 8 and I wasn't going to assume which one
  applies to a version I hadn't checked.
- `providers/redux-provider.tsx` — new. `ReduxProvider`: `<Provider store={store}>` wrapping
  `<PersistGate loading={null} persistor={persistor}>`. `loading={null}` (renders nothing
  until rehydration completes, no spinner) because no current page needs persisted state
  to render its first paint — revisit if that stops being true.
- `app/layout.tsx` — wraps `{children}` in `ReduxProvider` (outermost) then `QueryProvider`
  (from Entry 1). Order doesn't matter functionally (neither depends on the other) but
  Redux is the more foundational/session-wide piece of state, so it's outermost.
- `app/auth/login/page.tsx` — `onSuccess` now also `dispatch(setUser(data.user))`
  alongside the existing `localStorage.setItem("token", ...)` — deliberately **not**
  moved into Redux too in this pass; see Known gaps.

### Why
**Token stayed in raw `localStorage`, not Redux** — the user asked specifically for "user
data," and `lib/axios.ts`'s request interceptor (written before this session, in Entry 1)
already reads the token directly from `localStorage.getItem("token")`. Moving the token
into Redux+persist now would mean either duplicating it in two places or rewiring the
axios interceptor to pull from the persisted store outside of React — a real design
question or a Entry to itself, and going beyond what was asked. Flagged as a known gap
below rather than silently done or silently ignored.

**Slice lives in `features/auth/`, store config lives in `lib/`** — this splits "what is
user-domain state" (the slice) from "how the app wires up Redux at all" (config,
persistence, typed hooks), matching the same reasoning already applied to
`lib/axios.ts`/`lib/api-envelope.ts` (shared, feature-agnostic) vs.
`features/auth/api/`, `.../schemas/`, `.../hooks/` (auth-specific) in Entry 1.

### Invariants affected
None.

### Known gaps / TODO for the next agent
- **The access token still lives only in raw `localStorage`, separate from Redux.** If a
  future task wants "the whole session (user + token) in one place," that's a deliberate
  design decision (see Why) — likely either (a) add a `token` field to the same `user`
  slice and rewrite `lib/axios.ts`'s interceptor to read from the Redux store / a plain
  module-level getter instead of `localStorage` directly, or (b) leave the split as-is and
  treat "user profile" and "session token" as intentionally separate concerns. Not decided
  here — flag it explicitly rather than picking one silently if it comes up.
- **No `logout` action wired to anything yet.** `clearUser` exists on the slice but nothing
  calls it, and nothing clears the `localStorage` token either. A logout flow needs both:
  `dispatch(clearUser())` and `localStorage.removeItem("token")` — and probably
  `persistor.purge()` if a fully clean slate is wanted on logout, not just a rehydrated
  empty state.
- **Home page still renders hardcoded mock data** ("Jhon Doe", fixed balance), not the
  now-available `useAppSelector((s) => s.user.user)`. Wiring Home to the real persisted
  user was not part of this request — noted as the obvious next step, not done
  speculatively.

### Do NOT do
- Do not remove the `serializableCheck.ignoredActions` list from `lib/store/store.ts` "to
  clean it up" — those six action types are exactly the ones `redux-persist` itself
  dispatches with non-serializable payloads; removing the list reintroduces a console
  warning on every single app load, verified above to actually be silent with it in place.
- Do not add slices to `persistConfig.whitelist` by default — persistence is opt-in per
  slice on purpose (see What changed). A new slice that doesn't need to survive a reload
  should NOT be added to the whitelist just because it's easy to.
- Do not assume a blank/partially-rendered page in `claude-in-chrome` during local dev
  means something is broken — this session hit exactly that (missing logo, unresponsive
  input) purely from Turbopack's first-compile lag after adding new npm packages; wait and
  re-check before concluding there's a real bug.

## Entry 3 — Codify GORM as the mandatory ORM for all Go services (docs only)

- **time:** 10:27
- **agent:** Claude Sonnet 5 (Claude Code)
- **task:** "add gorm in our architecture docs so if other agents want to create new
  backend service they will also use gorm."
- **status:** completed
- **scope:** docs
- **touches_money:** no

### What changed
- `docs/CLAUDE.md` §5.4 (Backend / Go services) — added a mandatory-ORM rule matching the
  existing "Formik + Yup, no exceptions" pattern from §5.3: GORM is required for every Go
  service, no raw `database/sql`/`pgx` queries, no second ORM. Folded in, as sub-bullets,
  the four concrete traps actually discovered and fixed while building `user-service`
  (2026-08-21 Entry 2): never use `AutoMigrate` (schema stays explicit forward-only SQL
  files), open with `TranslateError: true` (so driver errors unwrap via `errors.As`),
  silence GORM's own logger (it bypasses structured JSON logging and mislabels expected
  outcomes like a duplicate-key conflict as "ERROR"), and keep GORM row-mapping structs
  separate from domain types.
- `docs/CLAUDE.md` §10 (Quick Reference) — added one line to the `DURING:` block: "Go
  services = GORM only, never AutoMigrate — migrations are explicit SQL files" — so the
  rule is visible in the compressed reference, not only buried in §5.4's full text.
- `docs/guides/Kimo-Wallet-Architecture.md` §13 (Database Ownership) — added a "Data
  Access" subsection naming GORM as the ORM, restating the AutoMigrate exclusion and the
  domain/row-struct separation at the architecture-doc level (the "what to build" doc),
  and pointing at `docs/CLAUDE.md` §5.4 for the full enforced rule (the "how to work" doc)
  — mirroring exactly how Formik/Yup is documented in both places (§15 there, §5.3 here).

### Why
GORM was already the de facto standard in this codebase (`user-service`, since
2026-08-21 Entry 2 — an explicit user request at the time, not previously written into
either doc as a rule for *future* services). The user's request today is specifically
about making that binding for the *next* backend service someone builds, not re-deciding
anything. Codifying it now, rather than leaving it as something only discoverable by
reading `user-service`'s source or the agent log, is exactly what prevents a future agent
building `wallet-service` or `transaction-service` from picking a different ORM (or
reaching for `AutoMigrate`) with no way to know that was already decided against and why.

Placed the detailed traps (AutoMigrate, TranslateError, logger silencing) in
`docs/CLAUDE.md` rather than only in the architecture doc, because `docs/CLAUDE.md` is
where this repo's other "no exceptions" library mandates live (§5.3's Formik+Yup rule),
and because these specific traps are "how to work" correctness/observability rules, not
"what to build" system design — matching the doc boundary the header of `docs/CLAUDE.md`
itself states explicitly.

### Invariants affected
None directly — this is a documentation-only change. It does affect what counts as a
correctness violation in future backend work (using `AutoMigrate`, or a second ORM, is
now a rule violation per §1/§9's Definition of Done, not just a style preference).

### Verification
- Read back both edited sections after writing them (`sed -n` over the exact line ranges)
  to confirm the Markdown rendered as intended — correct heading levels, no broken list
  nesting, the architecture doc's new subsection sits under §13 without disturbing the

- No code changed, so no build/lint/test run applies to this entry.

### Known gaps / TODO for the next agent
- This documents GORM as mandatory for **new** Go services going forward. It does not
  retroactively audit any other existing service for compliance — as of this entry,
  `user-service` is still the only backend service that exists, and it already follows
  every rule stated here (it's the reference implementation the docs point to).
- If a future service has a genuine reason GORM can't do what it needs (per §5.4's escape
  hatch — "say so and stop, do not silently reach for a second data-access library"),
  that's a real decision point requiring a human, not something to resolve unilaterally
  by picking a different library and moving on.

### Do NOT do
- Do not treat this as permission to go back and add `AutoMigrate` calls or a different
  ORM to `user-service` "for consistency with some other approach" — `user-service` is
  the reference implementation these new rules were written *from*, not the thing being
  brought into compliance.
- Do not remove the GORM mandate from `docs/CLAUDE.md` §5.4 while leaving it in the
  architecture doc (or vice versa) if either doc is edited later — they're written to
  mirror each other (architecture doc = what/why, CLAUDE.md = the enforced rule), same as
  the existing Formik/Yup split; keep both in sync if one changes.
