## Entry 1 — Transaction History page with verified infinite scroll

- **time:** 22:15
- **agent:** Claude Opus 5 (Claude Code)
- **task:** Create a transaction history page, styled like Home's "Latest Transactions" section, showing all transactions with infinite scroll using a React library
- **status:** completed
- **scope:** apps/web
- **touches_money:** no

### What changed
- `apps/web/components/layout/Page.tsx` — added `id="page-scroll-container"` to the scrollable
  wrapper, so any page can reference the app's single real scroll container (needed by the
  infinite-scroll library's `scrollableTarget` and by the history page's own scroll listener).
- `apps/web/features/transaction/types.ts` — new. Shared `Transaction`/`TransactionDirection`
  types: amount is a positive integer (whole Rupiah), sign comes from `direction`, not a
  pre-formatted string — separates data from display per the project's money-formatting rules.
- `apps/web/features/transaction/format.ts` — new. `formatTransactionDate` /
  `formatTransactionAmount`, verified against the existing hardcoded strings before use
  (`Intl.DateTimeFormat("en-GB", ...)` and `.toLocaleString("id-ID")` reproduce "15 Aug 2026,
  17:20" and "Rp 50.000" exactly).
- `apps/web/features/transaction/mock-transactions.ts` — new. `fetchTransactionsPage(page)`
  simulates a paginated API (600ms latency, fixed 120-item deterministic pool, 15/page). Swap for
  a real fetch once the transaction service exists — callers only depend on the signature.
- `apps/web/features/transaction/components/transaction-row.tsx` — new. `TransactionRow`,
  extracted from Home's existing markup so both pages render transactions identically instead of
  maintaining two copies.
- `apps/web/app/wallet/history/page.tsx` — new route. Sticky header with back nav, infinite-scroll
  list using `react-infinite-scroll-component` (new dependency) plus a defensive `scroll` listener
  (see Known gaps / Do NOT do — the library alone was not reliable).
- `apps/web/app/home/page.tsx` — linked the "History" menu button (previously a dead `<button>`
  with no destination) to `/wallet/history`; local transaction array retyped as `Transaction[]` and
  rendered via the shared `TransactionRow` instead of duplicated JSX.
- `apps/web/package.json` — added `react-infinite-scroll-component` (^7.2.1, IntersectionObserver-
  based, typed, React 17+ compatible).
- `docs/CLAUDE.md` §5.6.3 — appended traps #7 (flex items need `shrink-0` to overflow instead of
  compressing) and #8 (IntersectionObserver sentinel transition-only firing), both found and fixed
  in this session; retitled the section from "CSS traps" to "CSS and interaction traps" since #8
  isn't CSS.

### Why
The user asked for infinite scroll "using a react library" rather than hand-rolled
IntersectionObserver logic. Chose `react-infinite-scroll-component` over adding
`@tanstack/react-query` (which the architecture doc lists as a *potential* stack choice, not yet
used anywhere in the app) — a full query-caching framework for one mock-data page would be
scope beyond what was asked; the library actually requested is proportionate and self-contained.

Data is mock/simulated because no transaction-service backend exists yet (per the architecture
doc's current stage). Modeled as an integer amount + direction rather than a formatted string
specifically because docs/CLAUDE.md §3.3 rule 4 treats float/string-sign money data as a smell
even in mock UI data — cheap to do correctly now, and it's what a real API response would look
like.

The library swap-out (defensive `scroll` listener) exists because I tested it, not because I
assumed it. See Verification.

### Invariants affected
None — no money mutation, no ledger, no idempotency surface. Display-only mock data.

### Verification
- `npx tsc --noEmit`, `npx eslint <changed files>`, `npm run build` — all clean, `/wallet/history`
  present in the route table.
- **Visually verified via claude-in-chrome, not just build-clean** (per §5.6): navigated to
  `/wallet/history`, confirmed it renders identically to Home's transaction row style, confirmed
  the header back-link navigates to `/home`.
- **Found a real bug via testing, not assumption**: the library's own IntersectionObserver sentinel
  reliably stalled after 3–6 pages under fast/programmatic scrolling that lands exactly at the max
  scroll position in one motion (no intersection *transition* fires, so `next()` never re-triggers,
  even though `hasMore` is still true). Reproduced twice with different stopping points (45 items,
  then 90 items) before the fix. Confirmed the mechanism with `document.hasFocus()`/rect
  measurements via `javascript_tool`, not guesswork.
- **Fix verified against the exact adversarial scenario that broke it**: replayed the same
  aggressive multi-burst scroll sequence after adding a `scroll`-event backstop (refs, not state
  closures, to avoid staleness in a mount-only listener). Result: all 120 items loaded, correct
  end message shown, `distanceFromBottom: 0` with `hasEndMessage: true` — confirmed via direct DOM
  query (`document.getElementById("page-scroll-container")` metrics + `document.body.innerText`),
  not inferred from a screenshot.
- No console errors at any point (`read_console_messages`, `onlyErrors: true`).

### Known gaps / TODO for the next agent
- `react-infinite-scroll-component`'s sentinel is still mounted and does real work (it drove 3–7
  pages correctly on its own in testing) — the `scroll` listener is a backstop, not a replacement.
  Do not remove the library thinking the listener alone is sufficient elsewhere; the listener here
  is specific to this page's container and re-implementing it per-page is exactly the kind of
  duplication that should be extracted into a shared hook if a third infinite-scroll page appears.
- The mock pool is fixed at 120 items / 15 per page, generated once at module load in
  `mock-transactions.ts`. No error state exists because the mock function cannot fail — if this is
  later swapped for a real fetch, an error/retry state needs to be added (not present today, and
  intentionally absent per "don't add error handling for scenarios that can't happen").
- Home page's own 5-item "Latest Transactions" list is still a separate hardcoded array (now typed
  as `Transaction[]`), not sourced from `mock-transactions.ts`. Left deliberately separate — Home's
  data-loading behavior (synchronous, no spinner) wasn't part of this request and changing it would
  have been unrequested scope expansion. If Home is later wired to fetch real data, consider
  whether it should share the same source as History.

### Do NOT do
- Do not trust `react-infinite-scroll-component` (or likely any bare IntersectionObserver-sentinel
  pattern) to keep loading under fast/flick scrolling without a distance-from-bottom backstop. This
  is not a one-off fluke — it reproduced twice, at different stopping points, in this session.
- Do not read `page` or `hasMore` from component state inside a listener attached in a mount-only
  (`[]` dependency) `useEffect`. Use refs (`pageRef`, `hasMoreRef`) kept in sync, or the listener's
  closure goes stale and silently re-fetches the first page forever. See the current implementation
  in `app/wallet/history/page.tsx` for the working pattern.
- Do not delete or "simplify away" the `loadingMoreRef` guard in `loadMore` — it's what prevents
  the library's sentinel and the defensive `scroll` listener from double-fetching the same page
  when both fire close together.
