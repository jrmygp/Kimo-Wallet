## Entry 1 — Dead-letter topic for wallet-service's user.created consumer

- **time:** unknown
- **agent:** Claude Sonnet 5 (Claude Code)
- **task:** Close the "no real dead-letter mechanism" gap flagged in 2026-09-05 Entry 4: when `eventconsumer.Handler` exhausts its 5 retry attempts on a message, publish it to a dead-letter topic (preserved untouched, with diagnostic headers) instead of just logging and discarding its content.
- **status:** completed
- **scope:** apps/wallet-service, apps/user-service (one-line producer config fix, see below)
- **touches_money:** no

### What changed
- `apps/wallet-service/internal/kafkaproducer/producer.go` (new) — wallet-service's first producer (it was consumer-only before this). Duplicated from `user-service`'s own `kafkaproducer` package (separate Go modules, same reasoning as every other duplicated file between these two services) with one addition: `Publish` now takes a `headers map[string]string` parameter, since the dead-letter use case needs it and the outbox relay's producer never did.
- `apps/wallet-service/internal/eventconsumer/handler.go`:
  - New `DeadLetterPublisher` interface (`Publish(ctx, topic, key, value, headers) error`), a new `deadLetter` field on `Handler`, and a new `NewHandler` parameter for it.
  - `processWithRetry`: when `maxProcessAttempts` (5) is exhausted, calls the new `deadLetterOrLog` before committing — previously it just logged and moved on, discarding the message's actual content.
  - `deadLetterOrLog`: publishes to `<original-topic>.dlq` (e.g. `user.created.dlq`) with the message's `Value` **byte-for-byte untouched** — deliberately not wrapped in a new JSON envelope, since the payload that failed to parse is often exactly *why* it failed, and wrapping it would mean base64-encoding it defensively and requiring anything that later wants to replay it back to the original topic to unwrap it first. Diagnostic context (original topic/partition/offset, failure timestamp, attempt count, the error itself) travels instead as Kafka message headers (`x-original-topic`, `x-original-partition`, `x-original-offset`, `x-failed-at`, `x-attempts`, `x-error`) alongside the untouched value.
  - The dead-letter publish itself gets its own small bounded retry (`maxDeadLetterPublishAttempts = 3`, reusing the same `retryBackoff` field) — see Why below for the real bug this caught.
  - Committing the original message happens regardless of whether the dead-letter publish itself ultimately succeeds (after retries) — the alternative, blocking the partition indefinitely on a publish that might never succeed, is worse than the accepted rare case of a message lost from both places.
- `apps/wallet-service/cmd/server/main.go` — constructs a second `kafkaproducer.Producer` (the dead-letter one) alongside the existing consumer, wires it into `eventconsumer.NewHandler`, closes it on shutdown via `defer`.
- **`apps/user-service/internal/kafkaproducer/producer.go`** and **`apps/wallet-service/internal/kafkaproducer/producer.go`** — both `kafka.Writer` configs gained `AllowAutoTopicCreation: true`. Found live (see Why): without it, `kafka-go` treats "topic doesn't exist yet" as a hard error rather than ever asking the broker to create it at all.
- Tests (`handler_test.go`): extended `TestHandler_ProcessWithRetry_GivesUpAndDeadLetters` (renamed from the old `...GivesUpAndCommitsAfterMaxAttempts`) to assert the dead-lettered message's topic, key, value (byte-identical to the original), and every header. New `TestHandler_ProcessWithRetry_SuccessNeverDeadLetters` (happy path never touches the DLQ publisher). New `TestHandler_ProcessWithRetry_DeadLetterPublishRecoversAfterTransientFailure` — the exact real-world race this entry found live, reproduced as a stub-based unit test (fails once, succeeds on retry). `TestHandler_ProcessWithRetry_DeadLetterPublishFailureStillCommits` updated to expect `maxDeadLetterPublishAttempts` (3) attempts, not 1, and still committing after all of them fail.

### Why
**Payload untouched + headers for metadata**, not a JSON envelope wrapping everything: the whole reason a message ends up here is often that its content is malformed in some way — wrapping it in more JSON on top would compound exactly the problem that caused the dead-letter in the first place, and would force anything that later wants to try reprocessing it (copy the value back to `user.created`) to unwrap an envelope first instead of just resending the value as-is.

**The `AllowAutoTopicCreation` fix and the dead-letter-publish-specific retry were both found live, not designed upfront** — this is worth being explicit about since it's a real example of "verify, don't assume": the first live test produced a real malformed message onto `user.created`, and `wallet-service` correctly retried 5 times, gave up, and attempted to dead-letter it — but the dead-letter publish itself failed with `Unknown Topic Or Partition`. Root-caused by reading `kafka-go`'s own source (`writer.go`, `metadata.go`): `kafka.Writer.AllowAutoTopicCreation` defaults to `false`, so a `Writer` without it set never even *asks* the broker to create a missing topic — it just fails. Set it to `true` and retested: **still failed the same way**, but the topic now existed a few seconds later — meaning the broker *did* start creating it as a side effect of that request, but creation isn't synchronous with the metadata call that triggers it, so that same first request still reports the topic missing. This is a generally-known Kafka-client pitfall, not specific to this codebase. The fix needed both pieces: `AllowAutoTopicCreation: true` (so creation is requested at all) *and* a short bounded retry around the publish specifically (so the *first-ever* dead-letter to a brand-new DLQ topic doesn't get lost to this exact race). Retested a third time with both fixes: succeeded immediately, and every dead-letter after the first (once the topic exists) also succeeds on the first attempt — confirmed live twice.

This same latent gap (no `AllowAutoTopicCreation`) existed in `user-service`'s outbox-relay producer too, from Phase 2 (2026-09-05 Entry 3) — it just never surfaced there because the outbox relay retries every 2 seconds *forever* regardless of the reason for failure, so the same transient race silently self-healed on its own next tick. Fixed there too for consistency and correctness, even though nothing was actively broken-looking about it.

### Invariants affected
None (no money, no ledger, no balance mutation — this is entirely about not losing an unprocessable event's content).

### Verification
- `go build ./... && go vet ./... && gofmt -l .` — clean, both `apps/wallet-service` and `apps/user-service`.
- `go test ./...` (wallet-service) — all pass, including the 4 new/changed dead-letter-specific cases in `internal/eventconsumer` (8 total in that package).
- **Full live proof, three iterations, each one finding and then confirming a fix for a real issue — not a single "looks right" pass:**
  1. First attempt (pre-`AllowAutoTopicCreation`): produced a real malformed message (`{"userId": 12345, ...}`, an integer where the proto schema expects a string — the same example discussed earlier in conversation) directly onto `user.created` via `kafka-console-producer.sh`. Watched 5 real retries in the log, then a failed dead-letter attempt (`Unknown Topic Or Partition`).
  2. Second attempt (post-`AllowAutoTopicCreation`, pre-publish-retry): same failure, but confirmed via `kafka-topics.sh --list` moments later that the DLQ topic *had* been created — proving the fix was necessary but not sufficient on its own, and pointing directly at the real remaining gap (needs a retry, not just the flag).
  3. Third attempt (both fixes in place): produced another malformed message; watched the same 5 retries, then a clean dead-letter with **no failure logged this time**. Consumed `user.created.dlq` directly (`--property print.headers=true`) and confirmed the actual message: value byte-for-byte identical to the original payload, key preserved, and all six headers present with correct values (`x-original-topic:user.created`, `x-original-partition:0`, `x-original-offset:5`, `x-attempts:5`, `x-error:<the real unmarshal error>`, `x-failed-at:<real timestamp>`).
- Along the way, hit and resolved a confusing but ultimately mundane process-management issue: a `wallet-service` restart produced a `go run` wrapper with no compiled-binary child process and no further log output — investigated it as a possible second uncoordinated instance (there wasn't one; `ps`/`lsof` confirmed only one wallet-service process existed at any point), concluded it was a one-off transient failure of that specific `go run` invocation, and moved on after a clean restart produced the expected 3-process tree (shell wrapper, `go run`, compiled binary) every time after.

### Known gaps / TODO for the next agent
- **No replay tooling** — messages land safely in `<topic>.dlq` now, but there's no tool to inspect them nicely or resend them back to the original topic. Today that's a manual `kafka-console-consumer.sh`/`kafka-console-producer.sh` operation, same as this entry's own verification. Deliberately out of scope (per the plan agreed with the user before starting).
- `maxDeadLetterPublishAttempts` reuses `Handler.retryBackoff` (the same backoff as message-processing retries) rather than having its own tunable value. Fine for now; revisit only if there's an actual reason the two should differ.
- The dead-letter topic itself (`user.created.dlq`) currently has this session's manual test messages sitting in it (`poison-key`, `poison-key-2`, `poison-key-3`, `poison-key-final` — the middle two never actually made it into the DLQ, only the first and last did, per the investigation above). Harmless dev-only test data, not cleaned up.
- If `wallet-service` ever consumes more than one topic, `deadLetterTopicSuffix`'s `msg.Topic + ".dlq"` derivation already generalizes correctly (it's per-message, not hardcoded to `user.created`) — no change needed there when that day comes.

### Do NOT do
- Don't wrap the dead-lettered payload in a JSON envelope "to make it easier to add fields later" — the whole design point is that `Value` on the DLQ message is byte-for-byte what was on the original topic, so it can be resent there directly with zero transformation. New diagnostic fields belong in headers, not the value.
- Don't remove the `AllowAutoTopicCreation: true` fix or the dead-letter-publish retry thinking "the topic exists now, so it's fine" — the race is specifically about a topic's *first-ever* creation. It only ever bites once per topic, but it *will* bite on that first time, in any environment where the topic hasn't been pre-created, including a fresh deploy.

## Entry 2 — api-gateway aggregates wallet balance into GetUserByID (own profile only)

- **time:** unknown
- **agent:** Claude Sonnet 5 (Claude Code)
- **task:** The user built `wallet-service`'s gRPC server themselves this session (commit `7959cfa`, `packages/contracts/wallet/v1/wallet.proto` + `internal/grpcserver/wallet_server.go` + `main.go` wiring) — reviewed at each step (proto syntax errors, a missing `status.Error` argument, the gRPC server never actually being started, and a real concurrency bug in `main.go`'s shutdown `select`, all found and explained but *not* fixed by this session, per explicit "don't add anything" / review-only requests). This entry is the follow-on the user then asked for directly: make `api-gateway`'s `GET /v1/user/{kimoId}` include the looked-up user's wallet balance.
- **status:** completed
- **scope:** apps/api-gateway
- **touches_money:** no (read-only aggregation of an existing balance figure; no mutation)

### What changed
- **A privacy decision was surfaced and confirmed with the user before writing any code** (see Why): `GetUserByID` is used almost exclusively to look up *other* people (the Transfer search flow), so naively injecting wallet balance into it would let any authenticated user see any other user's balance just by knowing their KimoID. Presented three options (never expose balance / always expose it / expose only for the caller's own id); the user chose the last one.
- `apps/api-gateway/internal/config/config.go` — added `WalletServiceAddr` (`WALLET_SERVICE_GRPC_ADDR`, required, same fail-fast treatment as `UserServiceAddr`).
- `apps/api-gateway/.env` / `.env.example` — added `WALLET_SERVICE_GRPC_ADDR=localhost:50052`.
- `apps/api-gateway/cmd/server/main.go` — opens a second gRPC client connection (to `wallet-service`, same insecure-transport-for-now caveat as the existing `user-service` connection), constructs `walletv1.NewWalletServiceClient(...)`, passes both clients plus `logger` into `handler.NewUserHandler`.
- `apps/api-gateway/internal/handler/user_handler.go`:
  - New `walletServiceClient` interface (mirrors `userServiceClient`'s testable-subset pattern).
  - `UserHandler` gained `walletClient` and `logger` fields; `NewUserHandler`'s signature changed to `(client, walletClient, logger)`.
  - New `walletResponseBody{Balance int64, Currency, Status string}` and a new `Wallet *walletResponseBody` field on `userData` (the struct `GetUserByID`'s response uses — `Register`/`Login`'s `registerData`/`loginData` are untouched, they don't carry this field).
  - New `walletForOwnProfile(ctx, lookedUpUserID) *walletResponseBody` helper: reads the authenticated caller's identity via `jwtauth.ClaimsFromContext(ctx)` (the same claims `middleware.RequireAuth` already put on the context — nothing new added to auth itself), and **only calls the wallet client at all** if `claims.Subject == lookedUpUserID`. Returns `nil` (never an error) for a mismatched caller, missing claims, or a wallet-lookup failure — wallet enrichment never fails the request, since the user profile lookup itself already succeeded independently.
  - `GetUserByID` now calls this helper and includes its result in the response.
- `apps/api-gateway/internal/handler/user_handler_test.go` — added `stubWalletServiceClient` (tracks whether it was ever called, not just its return value) and a `testLogger()` helper; every existing `NewUserHandler(...)` call site updated for the new constructor signature; the existing `TestUserHandler_GetUserByID` table gained assertions that `wallet` is `nil` and the wallet client was never called when a request has no auth claims at all. Three new dedicated tests: `TestUserHandler_GetUserByID_IncludesOwnWallet` (the one case it should fire), `TestUserHandler_GetUserByID_OmitsWalletForOtherUsers` (the actual privacy guarantee — asserts the wallet client is never even *called*, not just that its result is discarded), `TestUserHandler_GetUserByID_WalletLookupFailureDoesNotFailRequest` (still 200, user data intact, wallet just omitted).

### Why
The privacy concern is the whole reason this entry has the shape it does: balance is inherently private financial data, and this endpoint's only real caller today (the Transfer search UI, built 2026-08-28) exists specifically to look up *other* people. Naively merging wallet data in would have turned "search anyone's KimoID" into "read anyone's balance." The chosen design (only fetch/expose for the caller's own id, verified via the already-authenticated JWT claims, not a new trust decision) means the same endpoint safely serves both the existing "look up a transfer recipient" use case (still never sees their balance) and a "view my own profile" use case (does), without a second endpoint or a request parameter that could be spoofed — the caller's identity comes from the already-verified token, never from anything the client sends about *which* user it claims to be.

`walletForOwnProfile` swallowing a wallet-lookup failure into `nil` rather than propagating it as a request-level error is deliberate, not an oversight: wallet provisioning is asynchronous (Kafka, from 2026-09-05's entries), so a user looking up their own profile moments after registering could legitimately have no wallet yet — that's an expected race, not a bug, and shouldn't turn an otherwise-successful profile lookup into a 500.

### Invariants affected
None — read-only, no balance mutation, no ledger, no new auth trust boundary (identity still comes entirely from the already-verified JWT).

### Verification
- `go build ./... && go vet ./... && gofmt -l .` — clean.
- `go test ./...` — all pass, including the 4 new/changed `GetUserByID` test cases (7 total for that handler now).
- **Full live proof against the real running stack**, not just unit tests: restarted `api-gateway` with this change (found and stopped the old instance precisely by matching `cwd`, per the established convention this month — confirmed the "still listening on 8080" false alarm right after was unrelated outbound Chrome traffic to a remote port 8080, not a leftover process). Registered a real user, waited for the async `user.created` → wallet-creation flow (2026-09-05's Kafka entries) to provision their wallet, then:
  - `GET /v1/user/{ownKimoId}` with their own token → `"wallet":{"balance":0,"currency":"IDR","status":"ACTIVE"}`.
  - Registered a second real user, then `GET /v1/user/{firstUser'sKimoId}` with the *second* user's token → `"wallet":null`, while `user` data (id, phone, name, KimoID) was still returned in full. Confirms the privacy boundary holds against the real service, not just a stub.

### Known gaps / TODO for the next agent
- `wallet-service`'s own `main.go` (built by the user, reviewed this session) had a real concurrency bug discussed but not fixed by me: `handler.Run(ctx)` was called synchronously instead of in a goroutine, meaning the shutdown `select` was unreachable until *after* the Kafka consumer already stopped — a crashed gRPC server would go completely unnoticed while the consumer kept running. Also missing `grpcServer.GracefulStop()` on shutdown. Whether this got fixed is not confirmed by this entry — check `apps/wallet-service/cmd/server/main.go`'s current state before assuming it's still broken or still fixed.
- No test exists yet at the `wallet-service` gRPC layer itself (`grpcserver.WalletServer`) — this entry only tested the api-gateway side (with a stub wallet client) and the real end-to-end path live. A dedicated `wallet_server_test.go` mirroring `user_server_test.go`'s pattern doesn't exist.
- Currency is always `"IDR"` today (hardcoded in `wallet-service`, per 2026-09-05's Phase 3 entry) — the aggregated response just passes that through as-is; nothing here assumes otherwise, but there's no multi-currency handling anywhere in this path either.

### Do NOT do
- Don't fetch the wallet before checking `claims.Subject == lookedUpUserID` "to simplify the code" — the check must gate the *call itself*, not just whether the result gets included in the response. Fetching-then-discarding would still mean `wallet-service` (and its logs, and any tracing) sees every search as a balance lookup, and it's one accidental log line or debug endpoint away from leaking it anyway. The tests specifically assert the wallet client is never *called*, not just that its result is filtered — don't weaken that assertion if this code is ever touched again.
- Don't make a wallet-lookup failure return an HTTP error from `GetUserByID` — see Why above; an unprovisioned wallet is an expected race, not a failure of the request that successfully found the user.

## Entry 3 — Login now also includes the caller's own wallet balance (fixing the user's broken draft)

- **time:** unknown
- **agent:** Claude Sonnet 5 (Claude Code)
- **task:** The user pasted a `Login` handler draft they had written themselves, asking for it to be fixed and to also show the user's wallet balance in the login response — the natural follow-on to Entry 2, which only did this for `GetUserByID`.
- **status:** completed
- **scope:** apps/api-gateway
- **touches_money:** no (read-only aggregation of an existing balance figure, same as Entry 2; no mutation)

### What changed
- `apps/api-gateway/internal/handler/user_handler.go`:
  - The user's pasted draft had four distinct bugs, all found and fixed: (1) an extra `ctx` parameter that broke the `http.HandlerFunc` signature `Login` must satisfy — removed, uses `r.Context()` like every other handler in this file; (2) a wallet-fetch failure caused an early `return` with nothing written to the response, silently turning a successful login into a hung/empty request — fixed by making wallet enrichment best-effort, never able to abort the request; (3) the wrong type was being assigned into the `Wallet` field; (4) `loginData` had no `Wallet` field at all yet.
  - Added `Wallet *walletResponseBody` to `loginData`, with a comment explaining it differs from `userData`'s `Wallet`: `Login` is always the caller looking up *themselves*, so there's no "someone else's balance" case to gate here, unlike `GetUserByID`.
  - Extracted a new shared `fetchWallet(ctx, userID) *walletResponseBody` — fetches and converts a wallet, swallowing any error into `nil` (never propagating it) rather than failing the caller's request. `Login` calls this directly with the just-authenticated user's id.
  - `walletForOwnProfile` (Entry 2, still used by `GetUserByID`) now delegates to `fetchWallet` for the actual fetch, keeping its own responsibility narrowed to just the caller-identity privacy gate. No behavior change for `GetUserByID`.
- `apps/api-gateway/internal/handler/user_handler_test.go` — two new tests: `TestUserHandler_Login_IncludesWallet` (successful login + successful wallet fetch → `wallet` populated with the stubbed balance/currency/status, and asserts the wallet client was actually called) and `TestUserHandler_Login_WalletLookupFailureDoesNotFailLogin` (wallet client returns a gRPC `NotFound` error → login still returns `200` with the access token intact and `wallet: null`, proving the bug class in point (2) above can't recur).

### Why
`fetchWallet` swallowing errors into `nil` is deliberate, for the same reason as Entry 2's `walletForOwnProfile`: wallet provisioning is asynchronous (Kafka — 2026-09-05's entries), so a user logging in moments after registering can legitimately have no wallet yet. That's specifically why the user's own draft was actually broken — an early `return` on wallet-fetch failure meant *any* wallet-provisioning race would silently break login itself, which is a much worse failure than the login endpoint the user was already relying on. Sharing `fetchWallet` between `Login` and `GetUserByID` (rather than duplicating the fetch-and-convert logic) keeps that best-effort behavior in exactly one place instead of two that could drift.

No new privacy decision was needed here (unlike Entry 2) — `Login` only ever returns data about the caller's own account, so there's no "someone else's balance" case to gate against.

### Invariants affected
None — read-only, no balance mutation, no ledger, no new auth trust boundary.

### Verification
- `go build ./... && go vet ./... && gofmt -l .` — all clean, no output.
- `go test ./...` — all pass, including the 2 new `Login`-wallet-specific tests (7 total for `TestUserHandler_Login*`).

### Known gaps / TODO for the next agent

The unit test (`WalletLookupFailureDoesNotFailLogin`) covers the *mechanism*, but the live race itself is untested end-to-end.

### Do NOT do

## Entry 4 — Register no longer starts a session; frontend redirects to Login instead

- **time:** unknown
- **agent:** Claude Sonnet 5 (Claude Code)
- **task:** Following on from Entry 3's finding (a freshly registered user's wallet is reliably `null` right after `Register`, because wallet provisioning is asynchronous via Kafka), the user asked for a new flow: `Register` no longer returns an access token at all — the newly registered user must call `Login` separately with their own phone number — and the frontend register page should redirect to the login page on success instead of auto-logging the user in.
- **status:** completed
- **scope:** apps/api-gateway, apps/web
- **touches_money:** no

### What changed
- **Found mid-edit, not starting from a clean base**: the user had already started this change themselves in `apps/api-gateway/internal/handler/user_handler.go` before asking — `Register` had been switched to build a `loginData{User, Wallet}` (dropping the explicit `AccessToken` assignment) instead of the dedicated `registerData` type, but `registerData` itself had also been trimmed to `{User, Wallet}` and left unused, the status code had accidentally become `200` instead of the original `201`, and `user_handler_test.go` still referenced `registerData.AccessToken`, which no longer existed — the package didn't compile (`env.Data.AccessToken undefined`). This entry finishes that change coherently rather than redoing it from scratch.
- `apps/api-gateway/internal/handler/user_handler.go`:
  - `registerData` is now `{User userResponseBody}` only — no `Wallet`, no `AccessToken`.
  - `Register` now builds `registerData{User: ...}`, restores `http.StatusCreated` (201, matching the original pre-session behavior and REST conventions for a create), and no longer calls `fetchWallet` at all — fetching wallet data that's never returned was pointless, and per docs/CLAUDE.md §5.1 ("no dead code") it's removed rather than left in place unused.
  - `Register`'s doc comment now explains *why*: registering creates the account but does not start a session; the client must call `Login` separately with the same phone number. This is also why going through `Login` incidentally sidesteps the wallet-provisioning race from Entry 3 — by the time a separate `Login` request happens, the async `user.created` → wallet-creation flow has usually already resolved.
  - **Deliberately did not touch `packages/contracts/user/v1/user.proto` or `user-service`.** `RegisterResponse.access_token` still exists in the contract and user-service still populates it — dropping it from the wire contract would be a breaking change requiring a new version directory (docs/CLAUDE.md §4 rule 4) for zero benefit, since the only consumer of this RPC is api-gateway, and api-gateway's HTTP response shape — what the frontend actually depends on — is exactly the kind of protocol-shaping api-gateway is supposed to own (§4 rule 2). Practically, the user does not get an access token, because api-gateway never surfaces the one user-service still mints internally.
  - `apps/api-gateway/internal/handler/user_handler_test.go` — `TestUserHandler_Register`'s success case now asserts, on the raw response bytes, that neither `"accessToken"` nor `"wallet"` appears anywhere in the body (not just that the decoded struct lacks the field — so this can't silently regress if someone re-adds the field to `registerData` without re-adding a value), and that the wallet client (`stubWalletServiceClient.called`) is never invoked by `Register` at all.
- `apps/web/features/auth/schemas/user-response.schema.ts` — split the single shared `userResponseSchema` (previously used for both Login and Register) into two: `userResponseSchema` (`{user, wallet, accessToken}`, still used by Login) and a new `registerResponseSchema` (`{user}` only, now used by Register). **Also fixed a latent bug found while touching this file**: `wallet` was not marked `.nullable()`, even though the backend can legitimately send a literal JSON `null` (Entry 2/3's best-effort wallet enrichment) — a plain `yup.object()` rejects `null` outright, so Login's response validation would have thrown on exactly the "wallet not provisioned yet" case this whole day's work has been about. Now `.nullable().defined()`, matching the pattern already used for `profilePicture`.
- `apps/web/features/auth/api/register.ts` — uses the new `registerResponseSchema`/`RegisterResponseData` instead of the shared one.
- `apps/web/app/auth/register/page.tsx` — on a successful register, no longer stores a token or dispatches `setUser` (removed the now-unused `useAppDispatch`/`setUser` imports entirely — nothing in this file reads `data` from the mutation result anymore). Instead stashes the phone number in `localStorage` under the same `"phoneNumber"` key/format the login page already uses (previously written by *login* when redirecting *here* on "user not found" — now written by *register* when redirecting *there*), and calls `router.push("/auth/login")`.
- `apps/web/app/auth/login/page.tsx` — now reads that same `localStorage["phoneNumber"]` on mount (identical pattern to what the register page already did for the reverse direction) to prefill `country`/`number`, with `enableReinitialize: true` and a fallback default of `"ID"` for country when nothing is stored. Clears it (`localStorage.removeItem("phoneNumber")`) in `onSuccess`, mirroring the removal timing the register page used to have.

### Why
The user-facing framing was "the newly registered user now would not get access token" — read literally as an HTTP-contract-level statement, not a request to touch JWT-minting in user-service. Keeping the token-minting internal to user-service (untouched) while api-gateway simply never surfaces it is the smallest change that satisfies that: one service touched, no proto/contract version bump, no change to user-service's tests or behavior.

Not fetching wallet in `Register` anymore isn't just "unused code cleanup" — it's the actual fix for Entry 3's underlying complaint. Nothing in the new flow ever shows a freshly-registered user `wallet: null`; that data simply isn't part of `Register`'s response shape anymore, and by the time `Login` is called (a separate request, initiated by the user acting on the redirect) the wallet is very likely to already exist.

Carrying the phone number forward via `localStorage` on the *register → login* redirect mirrors the exact mechanism this codebase already used for the *login → register* direction (2026-08-2x's original register/login integration) — reusing the established pattern rather than inventing a second one for the reverse direction.

### Invariants affected
None — no balance mutation, no ledger, no new auth trust boundary. Auth mechanics changed (Register no longer authenticates), but not who can access what once authenticated.

### Do NOT do
- Don't re-add `Wallet`/`AccessToken` to `registerData` or call `fetchWallet` from `Register` again without re-reading this entry and Entry 3 first — that's the exact race this flow change was designed to sidestep, not just an oversight to "fix" by adding the fields back.
- Don't assume `userResponseSchema` still covers Register's response shape — it's Login-only now; Register has its own `registerResponseSchema`. Using the wrong one will either wrongly require a `wallet`/`accessToken` that Register never sends, or wrongly accept a `wallet`/`accessToken` that shouldn't be there.
- Don't remove the `.nullable()` on `userResponseSchema`'s `wallet` field thinking it's unnecessary — a real, expected response (`wallet: null`, e.g. right after a login that races wallet provisioning) will fail schema validation without it, which is exactly the bug that was silently sitting there before this entry.
