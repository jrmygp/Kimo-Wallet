## Entry 1 — Fix Transfer menu button: sheet wouldn't reliably open + styling mismatch

- **time:** unknown
- **agent:** Claude Sonnet 5 (Claude Code)
- **task:** Fix the Transfer button on the home page so it opens its Sheet, and fix its styling to match the other menu buttons (Top Up, QR Code, History, Inbox, Settings).
- **status:** completed
- **scope:** apps/web
- **touches_money:** no

### What changed
- `apps/web/app/home/page.tsx` — `Sheet`'s `onOpenChange={() => setOpen(false)}` (always forced `false`, ignoring the boolean argument) changed to `onOpenChange={setOpen}`.
- `apps/web/app/home/page.tsx` — removed the `<a onClick={() => setOpen(true)}>` nested inside `SheetTrigger`. `SheetTrigger` renders as a native `<button>` (see `components/ui/sheet.tsx`), so nesting an anchor with its own click handler inside it was invalid HTML nesting and created two competing handlers racing on the same click.
- `apps/web/app/home/page.tsx` — `SheetTrigger`'s `className` changed from a copy-pasted Select-trigger style (`bg-background`, `shadow-xs`, `h-12`, ...) to `menuItemClassName`, the same class every other menu item (`Top Up`, `QR Code`, `History`, `Inbox`, `Settings`) uses, and its icon/label markup now matches those items' structure directly (`<span className={iconWrapperClassName}>` + `<p>`).
- `apps/web/app/home/page.tsx` — removed the now-unused `cn` import (it was only used by the className this change replaced).

### Why
The Sheet's controlled `open`/`onOpenChange` pair was fighting itself: `onOpenChange` always set `open` to `false` regardless of what was passed, so the workaround was a manually-added inner `<a onClick={() => setOpen(true)}>` — but that click bubbles up to the outer `SheetTrigger` button, which also fires `onOpenChange(true)`, immediately overridden back to `false` by the broken handler. Wiring `onOpenChange={setOpen}` directly (the standard controlled pattern, same idea as every other `useState` toggle in this file) fixes both directions correctly and lets `SheetTrigger` be used as intended — no manual click handler needed. Once the nested `<a>` was removed, `SheetTrigger` could be styled with the same `menuItemClassName` every sibling menu button already uses, instead of the mismatched Select-style classes, which fixes the visual inconsistency in the same change.

## Entry 2 — Search-user-by-KimoID wired into the Transfer sheet (search on Enter only)

- **time:** unknown
- **agent:** Claude Sonnet 5 (Claude Code)
- **task:** Integrate the existing GetUserByID endpoint (GET /v1/user/{id}) with the Transfer sheet's search UI (built in Entry 1's session, before this one): fire the search only when the user presses Enter (not on every keystroke), and show a user-list-item component with a placeholder Avatar for the result.
- **status:** completed
- **scope:** apps/web
- **touches_money:** no

### What changed
- `apps/web/features/wallet/schemas/user.schema.ts` (new) — Yup schema for the `User` shape returned by GET /v1/user/{id}. Deliberately separate from `features/auth/schemas/user-response.schema.ts`'s `userResponseSchema` (login/register's contract, which also carries `accessToken`) — different endpoint, different contract, even though the `User` fields match today.
- `apps/web/features/wallet/api/search-user.ts` (new) — `searchUserById(id)`, calling `GET /v1/user/{id}` via the shared `AxiosInstance` (bearer token attached automatically by its request interceptor), validated with the schema above, same try/catch → safe-message convention as `features/auth/api/login.ts` / `register.ts`.
- `apps/web/features/wallet/hooks/use-search-user-query.ts` (new) — `useSearchUserQuery(id)`, a `useQuery` (read-only, no side effect — see the doc-comment precedent in `useLoginMutation`), `enabled: id.length > 0`, `retry: false` (a miss is an expected "not found" outcome, not something to retry). The "only on Enter" behavior lives in the caller, not the hook: the hook just reacts to whatever `id` it's given, and `app/home/page.tsx` only updates that `id` on Enter, not on every keystroke.
- `apps/web/features/wallet/components/user-search-result-item.tsx` (new) — `UserSearchResultItem`, one result row: `Avatar` with a placeholder image (`https://github.com/shadcn.png`, same placeholder `TransactionRow` already uses) + initials `AvatarFallback`, full name, phone number. `role="option"` to match the existing `role="listbox"` container in the sheet.
- `apps/web/app/home/page.tsx` — added `searchId` state (only set from `query` on Enter, via a new `onKeyDown` on `InputGroupInput`), wired `useSearchUserQuery(searchId)`, and filled in the previously-empty `role="listbox"` div with four states: searching, error (`searchError.message`, `role="alert"`), found (`UserSearchResultItem`), and the initial empty-state hint. Also cleared `query`/`searchId` in the Sheet's `onOpenChange` when it closes, so reopening starts clean instead of showing a stale search.

### Why
GetUserByID is an exact lookup by id, not a fuzzy/list search, so the UI only ever shows zero or one result — no need for a results array or pagination. `useQuery` (not `useMutation`) matches this repo's existing convention for read-only calls; gating the actual fetch on a separately-committed `searchId` (set only by the Enter-key handler) rather than on `query` (updated every keystroke) is what makes it fire once per submission — `useMutation` would have worked too but would've broken from the `useLoginMutation`/`useRegisterMutation`'s established read-vs-write split for no benefit. A new `wallet` feature schema was added rather than reusing `userResponseSchema` from `features/auth` because that schema's contract includes `accessToken`, which GetUserByID's response doesn't have — reusing it would mean depending on an unrelated endpoint's contract accidentally staying compatible.

## Entry 4 — Fix GetUserByID returning 500 for a malformed (non-UUID) id

- **time:** unknown
- **agent:** Claude Sonnet 5 (Claude Code)
- **task:** After Entry 3's fix, the user reported still seeing 500 "internal error" when searching a nonexistent user. Live-debugged it: Entry 3's fix (well-formed-but-nonexistent UUID → 404) works correctly, but a **malformed / non-UUID id** still hits 500. Fix that too.
- **status:** completed
- **scope:** apps/user-service
- **touches_money:** no

### Correction to Entry 3
Entry 3's "Known gaps" said the two `go run` processes found on port 50051 were duplicates and killed both with the user's permission. Further debugging this session found that was a **misdiagnosis**: `lsof -ti:50051` matches both LISTEN and ESTABLISHED sockets, so it showed both user-service (the actual listener) *and* api-gateway (which holds an outbound gRPC **client** connection to user-service on that same port) — two different services, not two duplicate user-service instances. Killing api-gateway's process was unnecessary (though harmless — the user restarted both afterward). Leaving Entry 3 as written per docs/CLAUDE.md §2.2; noting the correction here.

### What changed
- `apps/user-service/internal/domain/user.go` — added `ErrInvalidUserID` sentinel error, `userIDPattern` regex (`^[0-9a-fA-F]{8}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{12}$`, matching the shape `idgen.NewV4` produces), and `NewGetUserByIDInput(id string) (string, error)` — same "shape-validate, return trimmed value or a sentinel error" pattern as `NewRegisterInput`/`NewLoginInput` right above it.
- `apps/user-service/internal/service/user_service.go` — `GetUserByID` now calls `domain.NewGetUserByIDInput(id)` first (mirrors how `Register`/`Login` call their own `New*Input` before touching the repo), so a malformed id is rejected before it ever reaches Postgres.
- `apps/user-service/internal/grpcserver/user_server.go` — `GetUserByID`'s switch gained a `case errors.Is(err, domain.ErrInvalidUserID): return nil, status.Error(codes.InvalidArgument, err.Error())`, ahead of the `ErrUserNotFound`/`NotFound` case added in Entry 3. api-gateway's `writeGRPCError` already had `codes.InvalidArgument` → 400 wired up (used by Register's phone/name validation), so no gateway change needed.
- `apps/user-service/internal/domain/user_test.go` — added `TestNewGetUserByIDInput` (valid lower/uppercase UUID, whitespace-trimming, empty, non-UUID string, a phone number, no hyphens, one hex digit short).
- `apps/user-service/internal/grpcserver/user_server_test.go` — added a `"malformed id maps to InvalidArgument, not Internal"` case to `TestUserServer_GetUserByID`.

### Why
Root cause: `id` is a Postgres `UUID` column (`migrations/0001_create_users_table.sql:2`). A non-UUID-shaped search string fails GORM's query with a Postgres uuid-parse error, not `gorm.ErrRecordNotFound` — so Entry 3's `errors.Is(err, domain.ErrUserNotFound)` check never matched it, and it fell through to the same `codes.Internal` default as any other unexpected infrastructure failure. Confirmed live via curl against the running gateway before writing any code: a well-formed nonexistent UUID → 404 (Entry 3's fix working correctly), a non-UUID string → 500 (the new bug). Validating the id's shape in the domain layer, before the repository call, is the same pattern already used for phone numbers/full names — rejecting bad input at the boundary rather than letting the database's own error type leak through as a generic 500.
