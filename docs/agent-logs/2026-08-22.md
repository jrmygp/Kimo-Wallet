## Entry 1 — Fix Login: unimplemented RPC + two repository bugs (found while user was building it live)

- **time:** 13:40
- **agent:** Claude Sonnet 5 (Claude Code)
- **task:** User was building a `Login` feature themselves across several files (proto,
  domain, service, repository, grpcserver, api-gateway handler) over the previous session
  and this one, largely unassisted, occasionally asking for help on specific pieces
  (GORM `Where()` usage, widening the api-gateway handler's client interface). This
  session: user reported hitting the live `/v1/auth/login` endpoint and getting
  `{"error":"internal error"}` with **no logs anywhere** — diagnosed and fixed.
- **status:** completed
- **scope:** apps/user-service (domain, service, storage/postgres, grpcserver)
- **touches_money:** no

### What changed
- **Root cause of the reported symptom** — `internal/grpcserver/user_server.go` had
  **no `Login` method at all**, only a commented-out stub
  (`// func (s *UserServer) Login(ctx context.Context, )`). Because `UserServer` embeds
  `userv1.UnimplementedUserServiceServer`, any `Login` RPC fell straight through to the
  generated fallback, which returns `codes.Unimplemented` **without executing any of the
  user's actual code** — which is exactly why there were no logs: nothing they wrote ever
  ran. `apps/api-gateway/internal/handler/respond.go`'s `writeGRPCError` has no case for
  `codes.Unimplemented`, so it fell into the generic `default → 500 "internal error"`
  branch. That chain (missing method → Unimplemented → unhandled-code → generic 500) is
  the entire explanation for the reported symptom.
  - Fixed: implemented `UserServer.Login` in `internal/grpcserver/user_server.go`, same
    shape as `Register` — calls `s.service.Login`, maps `ErrInvalidPhoneNumber` →
    `InvalidArgument`, the new `ErrUserNotFound` (see below) → `NotFound`, anything else →
    generic `Internal` (no message leak, same posture as `Register`).
  - Widened the `registrar` interface (renamed `userService`) to also declare `Login`,
    mirroring the exact same widening already done in `api-gateway`'s handler
    (`userRegisterer` → `userServiceClient`) for the same reason: the narrow test-seam
    interface needs to grow with the concrete type it stands in for.
- **`internal/domain/user.go`** — added `ErrUserNotFound` sentinel, following the existing
  pattern (`ErrPhoneNumberTaken` etc.) rather than a bare wrapped `gorm.ErrRecordNotFound`
  leaking a storage-layer error type up through the service/grpc layers.
- **`internal/storage/postgres/user_repository.go`'s `Login` method — two real, separate
  bugs found while implementing the fix, not previously caught because the method was
  never exercised against a real database until this session's test run:**
  1. `Where("phone_number = ?", input)` passed the whole `domain.LoginInput` struct as the
     query parameter instead of `input.PhoneNumber` (a string). GORM/pgx cannot bind a
     struct to a placeholder — this would have errored on every real call. Fixed to
     `input.PhoneNumber`.
  2. When the query error was *not* `gorm.ErrRecordNotFound`, the code had no `return` —
     execution fell through past the `if` block and returned a **zero-value `domain.User{}`
     with a nil error**, silently treating a real infrastructure failure as a successful
     lookup of an empty user. Fixed by returning immediately in both branches: the
     not-found case now returns `domain.ErrUserNotFound`, any other error returns wrapped
     (`fmt.Errorf("find user by phone number: %w", err)`).
- **Test coverage added** (none of this existed before, which is exactly how both
  repository bugs and the missing RPC survived until a live request hit them):
  - `internal/grpcserver/user_server_test.go` — `stubRegistrar` → `stubUserService` (adds
    `Login`), new `TestUserServer_Login` (success, `InvalidArgument`, `NotFound`,
    `Internal`-no-leak) alongside the existing `TestUserServer_Register` table.
  - `internal/storage/postgres/user_repository_test.go` — new
    `TestUserRepository_Login` (create then find, asserts full match) and
    `TestUserRepository_Login_UnknownPhoneNumber` (asserts `errors.Is(err,
    domain.ErrUserNotFound)`), run against real Postgres — these are exactly the tests
    that would have caught both repository bugs before a live request did.
  - `apps/api-gateway/internal/handler/user_handler_test.go` — already updated in the
    prior turn (stub widened, `TestUserHandler_Login` added) before this session's fix;
    unaffected by this entry, listed here only because it's part of the same feature.

### Why
This entry exists because the user was building Login mostly independently and hit a
production-shaped failure (generic 500, no diagnostic signal) rather than a compile error.
The fix path was: reproduce → read the actual server-side code path end to end (not just
the layer the error surfaced in) → find that `Login` was never implemented → find the two

### Known gaps / TODO for the next agent
- **Neither service logs anything on a request/error path** — only process-startup lines
  go through `slog`. This made this bug harder to diagnose than necessary ("no logs to be
  seen" was the user's first, correct observation). Worth adding at minimum a
  request-scoped error log (service name, method, gRPC code, trace/request id if one
  exists) in `grpcserver` and `handler` — not done here since it's a cross-cutting
  observability change, not part of fixing the specific Login bug, and deserves its own
  session rather than being bundled into a bug fix.
- `codes.Unimplemented` still has no explicit case in `api-gateway`'s
  `writeGRPCError` — it still falls into the generic `default → 500` branch. That's
  arguably fine (an unimplemented RPC *is* a server-side problem, 500 is defensible) but
  it will read exactly like this bug again to the next person if a *different* RPC is ever
  added to the proto and forgotten on the server side. Consider whether `Unimplemented`
  deserves its own explicit, more informative case — not changed here to keep this entry
  scoped to the actual bug.
- Password/PIN and any real session/token issuance for Login are still not implemented —

### Do NOT do
- Do not add a `Login`-shaped RPC to any `UserServiceServer` implementation by only
  editing the `.proto` and regenerating — the generated `UnimplementedUserServiceServer`
  fallback will silently accept the call and return `Unimplemented` with **zero
  application code executed**, which is indistinguishable from "working but doing
  nothing" until someone actually calls it. Always grep for the new RPC name in the
  concrete server implementation after regenerating, not just check that the build passes
  (embedding `Unimplemented...Server` means the build *always* passes even when a method
  is missing — that's the whole mechanism that hid this bug).
- Do not pass a struct directly as a GORM/database query parameter
  (`Where("col = ?", someStruct)`) expecting a field to be extracted automatically — it
  isn't; pass the specific field (`someStruct.Field`).
- Do not add an `if err != nil { if errors.Is(err, X) { return ... } }` block without an
  `else` (or a second `return` after the inner `if`) when there's code after the block
  that assumes success — the non-X-error case falls through and silently "succeeds" with
  zero-value data. This exact shape caused the second repository bug in this entry.

## Entry 2 — Standardised response envelope: {statusCode, message, data}

- **time:** 14:19
- **agent:** Claude Sonnet 5 (Claude Code)
- **task:** User asked for a standardised HTTP response shape across the gateway —
  success and error responses both carrying `statusCode`, `message`, and `data`, instead
  of the previous ad-hoc per-endpoint shapes (`{"user": {...}}` on success,
  `{"error": "..."}` on failure).
- **status:** completed
- **scope:** apps/api-gateway
- **touches_money:** no

### What changed
- `internal/handler/respond.go` — replaced `errorResponseBody{Error string}` with a
  single `apiResponse{StatusCode int, Message string, Data any}` envelope used by
  **every** response, success or error. `writeJSON` now takes `(statusCode, message,
  data)`; `writeError` is `writeJSON(w, statusCode, message, nil)` — `data` is always an
  explicit `null` on error, never an omitted key, so a client can rely on the shape
  without branching on which case it got. `writeGRPCError`'s status-code-mapping switch
  is unchanged — only the underlying write call's signature changed.
- `internal/handler/user_handler.go`:
  - `registerResponseBody` → `registerData`, `loginResponseBody` → `loginData` (renamed,
    same shape — `{"user": {...}}`) since they're now the `data` field's payload, not "the
    response body" (the response body is the whole envelope now).
  - `Register` success: `writeJSON(w, http.StatusCreated, "user registered successfully", registerData{...})`.
  - `Login` success: `writeJSON(w, http.StatusOK, "login successful", loginData{...})`.
- `internal/handler/user_handler_test.go` — updated all assertions to decode the envelope
  (`errorEnvelope`/`registerEnvelope`/`loginEnvelope` test-local types) instead of the old
  flat bodies: every case now also asserts `envelope.StatusCode == wantStatus` (not just
  the actual HTTP status) and, for errors, that `envelope.Data` decodes to `nil` — i.e. the
  test suite itself enforces the "data is always null on error" contract, not just checks
  it manually once.

### Why
**Success messages ("user registered successfully" / "login successful") are a judgment
call**, not something the user specified wording for — picked short, specific,
past-tense-of-the-action strings rather than a generic "success" for both, since a
specific message is more useful to a frontend that might just display `message` directly.
Cheap to change; flagging so it's not mistaken for a deliberate API contract already
agreed with a consumer (nothing consumes this yet).

**`data: null` explicit, not an omitted key on error** — chose explicit-null over
`omitempty` so the envelope's three keys are *always* present regardless of branch,
which is the point of "standardising" the shape: a client can do `response.data` without
first checking `if (response.error)`.

### Invariants affected
None. Pure response-shape change, no business logic touched — verified `writeGRPCError`'s
code-mapping switch is byte-for-byte unchanged, only the function it calls changed shape.

### Verification
- `go build ./...`, `go vet ./...`, `gofmt -l .` — clean.
- `go test ./... -v` — all 12 cases pass (6 Register + 1 oversized-body + 5 Login),
  including the tightened assertions that now check `envelope.StatusCode` and
  `envelope.Data == nil` on every error case, not just the HTTP status line.
- **Live verification over real HTTP**, not just unit tests: started the real compiled
  `user-service` and `api-gateway` against real Postgres (truncated `users` first for a
  clean run), then hit all four cases with `curl` and pretty-printed the actual JSON:
  - `POST /v1/auth/register` (new user) → `{"statusCode":201,"message":"user registered successfully","data":{"user":{...}}}`.
  - `POST /v1/auth/login` (same phone number) → `{"statusCode":200,"message":"login successful","data":{"user":{...}}}` — same user id as the register call.
  - `POST /v1/auth/login` (unknown phone number) → `{"statusCode":404,"message":"user not found","data":null}`.
  - `POST /v1/auth/register` (duplicate phone number) → `{"statusCode":409,"message":"phone number is already registered","data":null}`.
  All four match the requested shape exactly, read from real response bodies.
- Killed both server processes by actual listening PID (`lsof -ti:<port>`), confirmed both
  ports free and no `cmd/server` processes left running.

### Known gaps / TODO for the next agent
- The success message strings are hardcoded per-handler-method, not centralized — if a
  third endpoint is added, follow the same pattern (`writeJSON(w, status, "<past-tense
  description>", data)`), don't invent a different convention for wording.
- Still applies from Entry 1: `codes.Unimplemented` has no explicit `writeGRPCError` case
  and still falls into the generic `default` branch. Now that `default` also carries the
  envelope's `statusCode`/`message`/`data` shape (unchanged behavior, just the new
  envelope), this is unaffected but still worth revisiting per Entry 1's note.

### Do NOT do
- Do not go back to an omitted/`omitempty` `data` key on error responses — the whole point
  of this change was a client always seeing the same three top-level keys; `omitempty`
  would silently reintroduce the inconsistency this entry removed.
- Do not let a handler call the old flat shapes (`registerData`/`loginData`) directly as
  the top-level response body — they are the `data` *field's* payload now, always passed
  through `writeJSON(w, status, message, data)`, never written directly with
  `json.NewEncoder(w).Encode(...)`.

## Entry 3 — JWT access tokens + api-gateway auth middleware

- **time:** 14:33
- **agent:** Claude Sonnet 5 (Claude Code)
- **task:** "lets implement jwt token and prepare a middleware" — user-service mints a
  short-lived JWT on Register/Login; api-gateway gets reusable middleware to verify it and
  a minimal protected route to prove it works.
- **status:** completed
- **scope:** apps/user-service, apps/api-gateway, packages/contracts
- **touches_money:** no

### What changed
- `packages/contracts/user/v1/user.proto` — added `access_token` (field 2) to both
  `RegisterResponse` and `LoginResponse`. Regenerated for both consumers via
  `buf generate --template buf.gen.user-service.yaml` /
  `buf.gen.api-gateway.yaml` (the split from 2026-08-21 Entry 4 paid for itself again here
  — one command per consumer, no ambiguity about where output goes).
- **user-service (mints, never verifies):**
  - `internal/authtoken/token.go` — new. `Minter.Mint(userID, phoneNumber) (string, error)`,
    HS256, 15-minute `AccessTokenTTL`, claims = `jwt.RegisteredClaims{Subject: userID,
    Issuer: "kimo-wallet-user-service", IssuedAt, ExpiresAt}` + a custom `PhoneNumber`
    claim. `internal/authtoken/token_test.go` mints a real token and re-parses it with the
    same library to assert subject/phone/issuer/expiry, plus a wrong-secret-fails case.
  - `internal/config/config.go` — added required `JWT_SECRET` (fails fast if unset, same
    pattern as `USER_SERVICE_DATABASE_URL`).
  - `internal/service/user_service.go` — added a `TokenMinter` interface, injected via
    `NewUserService(repo, minter)`. `Register`/`Login` now return `(domain.User, string,
    error)` — user, access token, error — minting happens *after* the DB write/lookup
    succeeds, never before (a token for a user that failed to persist would be worse than
    useless).
  - `internal/grpcserver/user_server.go` — `userService` interface widened to the new
    3-return signatures; both RPCs now set `AccessToken` on their response.
  - `internal/grpcserver/user_server_test.go`, `cmd/server/main.go` — updated stub/wiring
    to match (minter constructed from `cfg.JWTSecret`, passed into `NewUserService`).
- **api-gateway (verifies, never mints):**
  - `internal/jwtauth/token.go` — new. `Verifier.Parse(tokenString) (*Claims, error)`,
    same `Claims` shape as user-service's `authtoken.Claims` (hand-kept in sync across the
    module boundary, not shared Go code — same reasoning as each service's own copy of
    generated protobuf code). Pins `jwt.WithValidMethods([]string{"HS256"})` explicitly —
    this is what stops an algorithm-confusion attack (e.g. a forged `"alg":"none"` token),
    and is covered by a dedicated test, not just assumed from the library's defaults.
  - `internal/jwtauth/context.go` — `WithClaims`/`ClaimsFromContext`, typed unexported
    context key. Lets `middleware` inject claims and `handler` read them back without the
    two packages depending on each other directly.
  - `internal/middleware/auth.go` — new package. `RequireAuth(verifier) func(http.Handler)
    http.Handler`: rejects with 401 on a missing/malformed `Authorization` header or a
    verification failure, otherwise injects claims into context and calls `next`.
  - `internal/httpresponse/` — new package, **extracted out of `handler`**: `Response`
    envelope + `WriteJSON`/`WriteError`, now used by both `handler` (unchanged behavior,
    routed through thin wrappers) and `middleware` (401s use the exact same envelope
    shape as everything else — a 401 from the middleware and a 400 from a handler look
    identical in structure). This is a real, needed refactor now that two packages write
    the same shape, not speculative sharing.
  - `internal/handler/user_handler.go` — `registerData`/`loginData` gained `AccessToken
    string \`json:"accessToken"\`` `. Added `Me(w, r)`: reads claims already verified by
    the middleware (`jwtauth.ClaimsFromContext`), returns `{id, phoneNumber}` — **does not
    call back into user-service**. This is a deliberate scope boundary: it exists to prove
    the middleware pipeline works end-to-end, not to be the real profile endpoint (PRD
    §7.1 "View their profile" would need a `GetUser` RPC that doesn't exist yet).
  - `internal/httpserver/router.go` — `NewRouter` now also takes `requireAuth
    func(http.Handler) http.Handler`; `GET /v1/users/me` is the only route wrapped in it.
    Register/Login stay unguarded — you cannot require a token to obtain one.
  - `internal/config/config.go`, `cmd/server/main.go` — added required `JWT_SECRET`,
    wired `jwtauth.NewVerifier(cfg.JWTSecret)` → `middleware.RequireAuth(...)` → router.
  - New tests: `internal/jwtauth/token_test.go` (valid token, wrong secret, expired token,
    **none-algorithm token — the algorithm-confusion attack test**, malformed string — 5
    cases, all against real signed tokens, not mocks). `internal/middleware/auth_test.go`
    (missing header, no-Bearer-prefix, empty-token-after-Bearer, verifier-rejects, and a
    success case that asserts claims actually landed in the downstream handler's context
    via a spy `next` — 5 cases). `internal/handler/user_handler_test.go` — Register/Login
    success cases now assert `AccessToken` is the exact value returned by the stub (they
    previously would have passed even with an empty token — tightened this), plus new
    `TestUserHandler_Me` (claims present) and `TestUserHandler_Me_WithoutClaimsInContext`
    (500, not a panic, if somehow called without going through the middleware).
- `.env.example` / `.env` in **both** services — added `JWT_SECRET` with matching
  comments explaining the two values must be identical (HS256 shared-secret) and that the
  committed placeholder is dev-only.

### Why
**user-service mints, api-gateway only verifies** — matches the architecture doc:
user-service owns "authentication-related data," the gateway's job is to "authenticate
incoming requests" (verify), not issue credentials for an identity it doesn't own.

**HS256 with a shared secret over RS256** — asymmetric key management (generate a
keypair, distribute the public key to the gateway, rotate both) isn't justified yet for a
single-team, pre-production project; HS256 is the boring default and trivially swappable
later if a genuinely separate-trust-domain gateway is ever needed. Made this call rather
than asking, since it's low-consequence at this stage (no real users, no production keys)
and easy to revisit — flagged clearly rather than silently assumed.

**Access token only, no refresh token / rotation / revocation** — that needs a sessions
table and rotation logic, which is new scope beyond "JWT + middleware." Same incremental
pattern as Register-then-Login (2026-08-21 Entries 1/Entry 1-of-22). A 15-minute TTL with
no refresh means re-`Login`-ing is currently the only way to get a new token — acceptable
for now, called out below as the next real gap.

**`GET /v1/users/me` as a demonstration route** — added it because an auth middleware
that protects nothing can't actually be proven to work end-to-end; a synthetic test alone
doesn't show the *wiring* (router → middleware → handler → context) is correct. Kept it
deliberately thin (claims-only, no user-service round-trip) so it doesn't masquerade as
the real profile endpoint.

**`internal/httpresponse` extraction** — not done speculatively; done because
`middleware` needed to write the exact same envelope shape as `handler` for 401s, and
duplicating the struct/functions between two packages *inside the same module* (unlike
the cross-module `Claims` duplication, which has an actual module-boundary reason) had no
justification.

### Invariants affected
None (no ledger, no balance, no idempotency surface). Auth/security-relevant, though —
see the money-adjacent testing rigor in Verification: this is exactly the kind of code
`docs/CLAUDE.md` §6 says needs care (authorization, no leaking internals, no weak crypto
defaults).

### Known gaps / TODO for the next agent
- **No refresh token.** 15-minute access tokens with no rotation/renewal — once expired,
  the only path back in is `Login` again. PRD §7.1 lists "Refresh an authenticated
  session" as a required capability; that's a real follow-up feature (sessions table,
  rotation, revocation-on-logout), not implemented here.
- **No token revocation / logout.** A minted token is valid until it expires; there is no
  server-side way to invalidate one early. Acceptable given the short TTL, but worth

  to the frontend before a revocation mechanism exists.
- **`GET /v1/users/me` is a demo route, not the real profile endpoint** — see Why. When a
  real "get my profile" feature is built, it should probably replace or extend this with
  an actual user-service `GetUser` RPC rather than trusting claims alone forever (claims
  are fine for identity, but a fresher `full_name`/etc. needs a real lookup).
- **`JWT_SECRET` is a checked-in dev placeholder** (`dev-only-shared-secret-please-...`)
  in both `.env.example` files and both real (gitignored) `.env` files. Fine for local
  dev; must be replaced with a real random secret (`openssl rand -base64 32` or
  equivalent) before this goes anywhere near a shared/deployed environment — same caveat
  as the Postgres password placeholder from 2026-08-21.
- No rate limiting on `/v1/auth/login` (someone could brute-force phone numbers against
  it, though there's no PIN/password to actually crack yet). Still blocked on the same
  Redis-requires-asking-first gap noted in 2026-08-21 Entry 4.

### Do NOT do
- Do not let api-gateway sign a token, ever — even for something that feels convenient
  (e.g. a gateway-only "session refresh" shortcut). Only user-service has signing logic
  (`internal/authtoken`); api-gateway only has `internal/jwtauth` (verify-only, no
  `SignedString` call anywhere in that package). If that boundary blurs, the "gateway
  holds no domain logic" architecture rule is what's being violated.
- Do not drop `jwt.WithValidMethods(...)` from `jwtauth.Verifier.Parse` "to simplify" —
  it's the specific line that makes the none-algorithm-confusion test pass. Removing it
  reopens a real, named class of JWT vulnerability, not a hypothetical one.
- Do not let `internal/authtoken.Claims` (user-service) and `internal/jwtauth.Claims`
  (api-gateway) drift apart without updating both. There is no shared Go type enforcing
  this — if user-service starts putting different data in the token, api-gateway's
  `Claims` struct needs the matching field added by hand, or that data silently won't
  parse.
- Do not point `GET /v1/users/me` (or any future protected route) at `handler`'s
  `writeJSON`/`writeError` inconsistently with `middleware`'s `httpresponse.WriteError` —
  they now resolve to the exact same underlying functions on purpose; don't reintroduce a
  second response-envelope implementation in a new package.
