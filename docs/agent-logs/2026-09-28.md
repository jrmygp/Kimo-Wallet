## Entry 1 — Design doc: settling a transaction (wallet debit/credit)

- **time:** unknown

- **touches_money:** yes (it's a design for money movement, though nothing here executes yet)

### What changed
- New `docs/plans/transaction-settlement.md` — the design for actually moving a balance between two wallets once `transaction-service.CreateTransaction` has recorded a `PENDING` transaction. Covers: an async two-hop Kafka round trip (`transaction.created` transaction-service→wallet-service, `transaction.processed` wallet-service→transaction-service), both reusing the transactional-outbox pattern already proven in this repo for `user.created`; a `ledger_entries` table design; deterministic wallet-lock ordering to avoid deadlock; idempotency at three layers (client idempotency key, Kafka redelivery on each topic); and a walkthrough against `docs/CLAUDE.md` §3.8's money-safety checklist. Three explicit open decisions left unresolved (single vs. split "processed" topic, whether to add an explicit `PROCESSING` status, how a caller polls for the outcome).

### Why
Documented a real correction made mid-discussion: an earlier verbal framing (in chat, never committed) had `transaction-service` owning `ledger_entries` alongside `transactions`. That's wrong — the ledger has to live in `wallet-service`'s database, because `docs/CLAUDE.md` §3.3 rule 3 requires the wallet's cached `balance` column to update in the *same* DB transaction as the ledger write, which is only possible if both live in the same database wallet-service already owns. Also: wallet-service holds both parties' wallets in one database, so it can debit+credit+ledger-write in a single atomic transaction — literally satisfying "a DEBIT and a matching CREDIT... written in one database transaction or neither is written," which would be structurally impossible if the ledger lived in transaction-service instead. This correction is called out explicitly in the plan document itself so it isn't lost.

The async/outbox choice over a synchronous debit/credit RPC was the user's own explicit decision ("i like the second option, more safe and sound more technical") after being shown the tradeoff: synchronous is simpler but creates a distributed-transaction problem (debit succeeds, credit fails, or a mid-flight crash, with no clean way to unwind); the outbox approach reuses this repo's own proven durable-event pattern instead of inventing compensation logic.
