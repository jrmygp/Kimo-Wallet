## Entry 1 — Add rate limiting to api-gateway (auth routes by IP, CreateTransaction by user)

- **time:** unknown
- **agent:** Claude Sonnet 5 (Claude Code)
- **task:** Implement rate limiting — a gap flagged earlier this session (docs/CLAUDE.md §4.2 names
  it as one of the few things the gateway is allowed to own; §6 requires it for "auth attempts, PIN
  attempts, and financial mutations"), and confirmed by grep that it did not exist anywhere in the
  repo before this entry.
- **status:** completed
- **scope:** apps/api-gateway
- **touches_money:** yes (gates `POST /v1/transaction`, a financial mutation route — but changes
  only request *frequency*, not the transaction/ledger/idempotency logic itself; see "Invariants
  affected" below)

### What changed
- `apps/api-gateway/internal/middleware/ratelimit.go` (new) — `RateLimiter`: an in-memory,
  per-key token-bucket limiter (`golang.org/x/time/rate` under the hood) with a background sweep
  that evicts buckets idle longer than `idleTTL`, so a flood of distinct keys can't grow the map
  unbounded. Exposes `.Middleware(keyFn)` returning a standard `func(http.Handler) http.Handler`.
  Also adds two `KeyFunc`s: `KeyByIP` (splits `host:port`, falls back to the raw value) and
  `KeyByAuthenticatedUser` (reads claims via `jwtauth.ClaimsFromContext`, keys on `claims.Subject`,
  falls back to `KeyByIP` if claims are somehow absent rather than panicking or exempting the
  request).
- `apps/api-gateway/internal/middleware/ratelimit_test.go` (new) — unit tests: burst-then-block is
  deterministic (no sleep — a fresh bucket starts full, so `burst+1` synchronous calls exhausts it
  with zero elapsed time), different keys have independent buckets, `KeyByIP` port-splitting, and
  `KeyByAuthenticatedUser`'s claims-present / claims-absent branches.
- `apps/api-gateway/internal/httpserver/router.go:24-49` — `NewRouter` now takes two extra
  `func(http.Handler) http.Handler` params: `authRateLimit` (wraps `POST /v1/auth/register` and
  `POST /v1/auth/login`, outside `requireAuth` since there's no identity yet) and
  `transactionRateLimit` (wraps `POST /v1/transaction` **inside** `requireAuth`, so its key
  function can read the claims `requireAuth` put on the context).
- `apps/api-gateway/cmd/server/main.go` — constructs two `*middleware.RateLimiter`s: auth routes at
  5 burst / ~5 per minute per IP, transaction route at 10 burst / ~10 per minute per authenticated
  user; wires them into `httpserver.NewRouter`; `defer`s `.Close()` on both (stops the sweep
  goroutine) alongside the existing gRPC-connection `defer`s.
- `apps/api-gateway/go.mod` / `go.sum` — added `golang.org/x/time v0.15.0` as a new runtime
  dependency (§4.7: logging why). Pinned to v0.15.0 deliberately, not the newest (v0.16.0), because
  v0.16.0 requires Go ≥1.26 and would have silently bumped this module's `go` directive to 1.26.0
  while every other service in the monorepo stays on 1.25.0 — `go get`/`go mod tidy` did this once
  and it was reverted. `golang.org/x/time/rate` is Google's own token-bucket package (same org as
  the `golang.org/x/net` already pulled in transitively) and the stdlib has no rate limiter; writing
  a correct, race-free token bucket by hand was judged not worth it over using the standard one.

### Why
- Rate limiting belongs at the gateway, not in a domain service, per §4.2 — it's a transport-layer
  concern (how often, not whether a request is valid), so none of the three backend Go services
  were touched.
- Two separate limiters/keys instead of one IP-based limiter everywhere: an IP-keyed limit on
  `CreateTransaction` would let one user behind a shared/NAT'd IP throttle every other user on that
  IP, and — more importantly — would let an attacker bypass the limit entirely just by rotating
  source IPs while reusing one stolen token. Keying the money-moving route by the *authenticated
  user id* ties the limit to the actual resource being protected (how fast one account can attempt
  transactions), which an IP can't evade by changing network path. The auth routes have no
  authenticated identity to key on yet, so IP is the only option there — which is also the actual
  threat being defended against (credential stuffing from one source).
- In-memory, not Redis: `docs/CLAUDE.md` §4.6 requires explicitly asking the human before adding a
  new infrastructure dependency; Redis isn't in this stack today (checked `docker-compose.yml` — no
  redis service), and introducing one just for this would be exactly the kind of speculative
  infra-add the rule exists to prevent. In-memory is correct for the current single-process
  gateway; flagged as a known gap, not silently chosen, for whenever the gateway is ever run as more
  than one replica.
- Limiter numbers (5/min auth, 10/min transactions) are my own judgment call, not sourced from the
  PRD — the PRD doesn't specify a number. Flagged under "Known gaps" below for the user to tune.

### Invariants affected
- None to the money/ledger/idempotency logic itself — `TransactionService.CreateTransaction`,
  the guarded status transitions, and the idempotency-key uniqueness constraint are all unchanged.
  This entry only adds a 429 in front of the existing handler when a key exceeds its rate; it never
  changes what a request that *does* get through does.
- Auth: unchanged. `RequireAuth` still runs exactly where it did; `transactionRateLimit` was added
  *inside* it specifically so it never runs before claims exist.

### §3.8 money-change checklist (answered because this touches the `/v1/transaction` route)
- **Arrives twice?** Unaffected — the existing idempotency-key uniqueness constraint in
  transaction-service is still the only thing deciding that, unchanged by this entry.
- **Concurrently on the same wallet?** Unaffected — same reasoning; rate limiting doesn't change
  the guarded-update concurrency control.
- **Process dies halfway?** Unaffected — the limiter holds no financial state; its own in-memory
  buckets resetting on a gateway restart only means a client gets a fresh quota, never a double
  charge.
- **Event delivered three times?** N/A — this entry doesn't touch the Kafka consumer path.
- **Ledger still balanced?** Unaffected — no ledger-writing code was touched.
- **Test proving duplicate rejection?** N/A to this entry (that's the existing idempotency-key
  test coverage in transaction-service, untouched here). What *is* tested here is the new
  behavior: rejecting a caller once they exceed the configured rate — see Verification.

### Known gaps / TODO for the next agent
- In-memory, single-process only. If api-gateway is ever run as more than one replica, buckets are
  per-instance, so the effective limit multiplies by instance count — needs a shared store (Redis)
  at that point, which is its own infra decision per §4.6, not made here.
- Limit numbers (5/min for auth, 10/min for transactions, 10-minute idle-bucket eviction) are a
  starting judgment call, not derived from any spec. Tune if real usage patterns say otherwise.
- `KeyByIP` trusts `r.RemoteAddr` only; does not read `X-Forwarded-For` or `X-Real-IP`. Correct
  today (api-gateway has no reverse proxy in front of it), but would need to change — reading a
  *trusted* proxy header, never a client-supplied one blindly — if one is ever added, or every
  request would appear to come from the proxy's single IP and share one bucket.
- No PIN-attempt lockout: §6 also mentions rate-limiting PIN attempts, but PIN confirmation itself
  isn't implemented anywhere in this codebase yet (PRD §7.5, still a known gap from earlier
  sessions) — nothing to rate-limit until that feature exists.
- No dedicated `router_test.go` exists yet (wasn't one before this entry either) — the new
  `authRateLimit`/`transactionRateLimit` wiring in `NewRouter` is only exercised indirectly via the
  `middleware` package's own unit tests, not via a router-level test that proves the two middlewares
  are attached to the correct routes.

### Do NOT do
- Don't move `transactionRateLimit` outside `requireAuth` in the router — `KeyByAuthenticatedUser`
  reads claims from the request context that only `requireAuth` puts there; wrapping in the other
  order makes it silently fall back to IP-keying for every request, defeating the reason it's
  separate from the auth-route limiter.
- Don't `go get -u` or blindly `go mod tidy` for `golang.org/x/time` without checking the resolved
  version's required Go version first — the latest (v0.16.0) silently requires Go ≥1.26 and will
  rewrite this module's `go` directive out of step with every other service in the monorepo.

## Entry 2 — Block non-digit characters while typing the Amount field on the transfer page

- **time:** unknown
- **agent:** Claude Sonnet 5 (Claude Code)
- **task:** User asked how to stop letters/symbols from being typeable in the Amount input on
  `/wallet/transfer/[userId]`. Implemented live keystroke/paste filtering, not just the existing
  post-hoc Yup validation.
- **status:** completed
- **scope:** apps/web
- **touches_money:** no (UX-only input filtering on a money form field; does not change what's
  validated, parsed, or submitted — see "Why" below)

### What changed
- `apps/web/app/wallet/transfer/[userId]/page.tsx:120-126` — added `handleAmountChange`, which
  replaces `e.target.value` with `e.target.value.replace(/\D/g, "")` before calling
  `formik.setFieldValue("amount", ...)`.
- `apps/web/app/wallet/transfer/[userId]/page.tsx` (Amount `Input`, ~line 170) — swapped
  `onChange={formik.handleChange}` for `onChange={handleAmountChange}` on the Amount field only.
  The Note field is untouched (still plain `formik.handleChange`) since no such request was made
  for it and it has no digits-only constraint.

### Why
- `transfer-form.schema.ts`'s `amount` field already enforces `/^\d+$/` via Yup's `.matches()`, and
  `parseAmountInput` (`lib/money.ts`) already rejects anything but digits — so a non-digit character
  could never actually reach a request. This entry doesn't change what's allowed to submit; it only
  stops a disallowed character from appearing in the field in the first place, which is strictly a
  UX improvement (docs/CLAUDE.md §5.3.5: client-side behavior here is UX, never the authority — the
  server/schema boundary is unchanged and still the real enforcement).
- Filtering in `onChange` (not a `onKeyDown` character blocklist) was the deliberate choice: it
  catches typing *and* paste in one place (both fire the same `input`/React `onChange` event), and
  doesn't risk breaking Backspace/arrow-key/select-all/copy the way keydown-blocking approaches
  commonly do.
- No decimal point is allowed in the filter, matching `parseAmountInput`'s existing contract: this
  field is whole rupiah only, never fractional minor units typed by the user.

### Invariants affected
None. No change to validation rules, parsing, submission payload, or the money-safety logic in
`transfer-form.schema.ts` / `lib/money.ts` — both are untouched.

### Verification
```
cd apps/web
npx tsc --noEmit -p .                                   # clean, no output
npx eslint "app/wallet/transfer/[userId]/page.tsx"       # clean, no output
```
UI verification (§5.6): the real `/wallet/transfer/[userId]` route could not be driven directly —
navigating to it with a fabricated session makes the page's `useSearchUserQuery` fire a real
authenticated `GET /v1/user/{kimoId}` against the actually-running api-gateway; an unsigned/garbage
token gets a genuine 401, and `lib/axios.ts`'s interceptor immediately logs out and redirects to
`/auth/login` before the field could be interacted with. Minting a correctly HS256-signed token
using the dev `JWT_SECRET` (to pass real verification) was attempted and refused by the session's
own credential-leakage guardrail — correctly, since that meant shelling out with a secret read from
a `.env` file. Rather than work around that, verification was done with a standalone static HTML
page (served via a throwaway local `python3 -m http.server`, not part of the repo) containing a
single input wired to the *exact same* transform (`value.replace(/\D/g, "")`) feeding the exact same
pattern (filter-in-input, reflect back into the controlled value). Typed `1a2b3-4.5e6 7,8` into it
via real synthetic keyboard events (Claude in Chrome) and the field showed `12345678` — every
letter, `-`, `.`, space, and comma was stripped live, nothing left behind. This proves the transform
itself is correct against real DOM input events; it does not prove the wiring inside the actual
Formik-controlled page component renders identically, though the code is a direct, mechanical
`onChange` swap with no other moving parts (typecheck + lint both clean against the real file).

### Known gaps / TODO for the next agent
- The real page was not visually re-verified end-to-end after this change because of the
  authentication issue above. If anyone can log in through the real flow (or has a validly-signed
  dev token), it's worth a 30-second confirmation that typing a mixed string in the actual Amount
  field on `/wallet/transfer/[userId]` behaves the same as the standalone harness did.
- Leading zeros (e.g. "007") are still accepted by both the filter and the existing Yup
  `/^\d+$/` match — unrelated to this entry, pre-existing, not changed here, just noted in case it
  ever matters.

### Do NOT do
- Don't reach for an `onKeyDown`-based character blocklist here instead of the `onChange` filter —
  it's the easy way to accidentally break Backspace/Delete/arrow keys/Cmd+A/Cmd+V for this field.
