### Why
User explicitly scoped Register to phone number + full name only — no PIN, password, or
session/token issuance in this pass. That's a deliberate incremental-build decision, not
a PRD deviation: `docs/guides/Kimo-Wallet-PRD.md` §7.1/§7.4 lists PIN and full auth as
part of the Auth feature set, but building it all in one RPC would mean guessing at PIN
policy, hashing, and token/session design the user hasn't specified yet. Register-only
now, login/PIN as a separate, explicitly-requested next step, keeps each step reviewable.

Two infrastructure decisions were confirmed with the user before scaffolding (per §4.6,
"do not add infrastructure without the human explicitly asking"): gRPC+Protobuf now
(matching the architecture doc) over a temporary HTTP-only service, and Docker Compose
for local Postgres over an assumed pre-existing local instance.

Phone number modeled as a single E.164 string (matching the `+62...` example already used
in `apps/web`'s Home page mock data and the existing `country-code-select` component's
output shape) rather than separate country-code/local-number fields — one canonical wire
format, parsed once.

### Invariants affected
None directly (no ledger, no balance, no idempotency-key surface — registration isn't a
financial mutation). The one integrity invariant that *does* apply — a phone number must
map to at most one user — is enforced at the database constraint layer, not just
application logic, and is covered by a concurrency test (see Verification).

## Entry 2 — Switch user-service persistence from raw pgx to GORM

- **time:** 21:37
- **agent:** Claude Sonnet 5 (Claude Code)
- **task:** User explicitly asked to use GORM as the ORM instead of raw pgx. Replace the
  Register persistence layer accordingly; keep behavior identical.
- **status:** completed
- **scope:** apps/user-service
- **touches_money:** no

### What changed
- `go.mod` — added `gorm.io/gorm` and `gorm.io/driver/postgres` (direct dependencies).
  `github.com/jackc/pgx/v5` stays as a dependency (now indirect via the gorm driver, and
  still directly imported in `user_repository.go` for `*pgconn.PgError` — see below);
  `pgxpool` specifically is no longer used anywhere.
- `internal/storage/postgres/db.go` — new. `Open(dsn) (*gorm.DB, error)`: opens GORM with
  `TranslateError: true` (so a unique-constraint violation still comes back wrapped around
  the underlying `*pgconn.PgError`, same as before) and `Logger: logger.Default.LogMode(logger.Silent)`.
  GORM's default logger writes plain-text lines straight to stdout and logs expected
  outcomes (e.g. a duplicate phone number) as "ERROR" — both conflict with §5.4's
  structured-JSON-logs requirement, so it's silenced; the service's own `slog`-based
  logging in `grpcserver`/`main.go` is what actually gets logged. Verified this actually
  suppresses the noisy output — see Verification.
- `internal/storage/postgres/user_repository.go` — rewritten on `*gorm.DB`. Added a
  `userModel` GORM row type (`gorm:"primaryKey"` on ID, default snake_case naming for the
  rest — matches the existing `users` columns exactly, verified against the real schema,
  not assumed) kept separate from `domain.User` so the domain package stays ORM-tag-free.
  `Create()` still does a single `INSERT` and still detects "phone number taken" by
  `errors.As`-ing for `*pgconn.PgError` with code `23505` and the specific
  `users_phone_number_key` constraint name — same logic as the pgx version, same reason:
  precise to *this* constraint, not "any unique violation," in case another unique index
  is added later. `CreatedAt` is no longer read back via `RETURNING`; GORM's naming
  convention (`internal/storage/postgres/db.go` comment + verified in
  `gorm.io/gorm@v1.31.2/schema/field.go`) auto-populates any field literally named
  `CreatedAt` of type `time.Time` on `Create()`, so the DB-side `DEFAULT now()` in the
  migration is now a backstop, not the source of truth for this value.
- `internal/storage/postgres/migrate.go` — signature changed from `*pgxpool.Pool` to plain
  `*sql.DB` (`Exec`→`ExecContext`, `Begin`→`BeginTx`, etc.). **Migrations still do not go
  through GORM** — no `AutoMigrate`, no GORM model tags driving schema. Schema stays owned
  by the explicit, forward-only SQL files in `migrations/`, applied by this same
  hand-rolled runner as before. This was a deliberate decision, not an oversight: GORM's
  `AutoMigrate` synchronizes schema from struct tags at runtime, which conflicts directly
  with docs/CLAUDE.md §5.4 ("migrations are forward-only and additive... never edit a
  migration that has been applied") and with the architecture doc's explicit
  `migrations/` directory — a migration you can't review in a diff before it runs against
  a real database is exactly what this project's rules are trying to prevent.
- `cmd/server/main.go` — `pgxpool.New` → `postgres.Open`; extracts `*sql.DB` via
  `db.DB()` for the migration runner (kept decoupled from GORM, see above) and passes the
  `*gorm.DB` to `NewUserRepository`. `defer sqlDB.Close()` replaces `defer pool.Close()`.
- `internal/storage/postgres/user_repository_test.go` — `newTestPool` → `newTestDB`,
  returns `*gorm.DB`; `TRUNCATE`/`COUNT` queries now go through `db.Exec(...)` /
  `db.Raw(...).Scan(...)` instead of pgx pool methods. Test *behavior* and assertions are
  unchanged — same three cases, same pass/fail criteria.
- `internal/service/user_service.go`, `internal/domain/user.go`, `internal/grpcserver/*` —
  **untouched.** The `service.UserRepository` interface boundary meant the ORM swap was
  contained entirely to the `internal/storage/postgres` package and `main.go`; this is the
  interface paying for itself.

### Why
Explicit user request ("i want to use gorm as orm please"), not a technical necessity —
the pgx version had no defect. Per docs/CLAUDE.md §4.7 ("do not add a runtime dependency
without stating why the stdlib or an existing dependency is insufficient, log it"): the
honest reason here is preference/ergonomics for future services, not insufficiency of pgx.
Flagging that explicitly rather than retroactively justifying it as a technical need.

Verified real GORM API behavior before writing code instead of relying on training-data
recall: `go doc` for `gorm.Open`, `gorm.Config` (`TranslateError`, `Logger`), `gorm.DB.DB()`,
`gorm.DB.WithContext`, `gorm.ErrDuplicatedKey`, and `schema.NamingStrategy`; read
`gorm.io/driver/postgres@v1.6.2/error_translator.go` directly to confirm pgcode `23505`
really does map through to a wrapped `*pgconn.PgError` (not just a generic sentinel with
the detail thrown away) before relying on that in the repository's error handling; read
`gorm.io/gorm@v1.31.2/schema/field.go` to confirm the `CreatedAt` auto-timestamp
convention rather than assuming it.

### Invariants affected
None. Same as Entry 1 — registration is not a financial mutation. The phone-number
uniqueness invariant is unchanged and still enforced at the database constraint level, not
by GORM or application logic; this session added a concurrency test *re-run* (same test,
new persistence layer) to confirm the guarantee still holds through GORM, not just pgx.

### Verification
- `go build ./...`, `go vet ./...`, `gofmt -l .` — all clean.
- `go test ./...` (no real DB) — unaffected packages (`domain`, `grpcserver`) unchanged and
  passing; `storage/postgres` integration tests correctly `SKIP` with the same message as
  Entry 1 when `USER_SERVICE_TEST_DATABASE_URL` is unset.
- Real Postgres (same `kimo-wallet-user-db-1` container from Entry 1, still running) —
  `USER_SERVICE_TEST_DATABASE_URL=postgres://kimo:changeme@localhost:5433/kimo_user?sslmode=disable go test ./internal/storage/postgres/... -v -run TestUserRepository`:
  - First run (before silencing GORM's logger): all 3 tests passed, but output showed
    GORM printing raw, ANSI-colored, non-JSON lines to stdout for the duplicate-key case,
    including the string `"ERROR: duplicate key value violates unique constraint..."` for
    what is actually a correctly-handled, expected business outcome — this is what drove
    the `Logger: logger.Default.LogMode(logger.Silent)` change above, found by testing,
    not anticipated in advance.
  - Second run (after the logger change): identical 3/3 pass, zero extraneous output —
    confirmed the fix actually suppressed it, not just assumed it would.
- Started the real compiled server (`go run ./cmd/server`) against the same Postgres,
  confirmed structured JSON logs only (`migrations applied`, `grpc server listening`) —
  no GORM noise mixed in.
- Ran the same temporary e2e gRPC client approach as Entry 1 (written, used, deleted —
  not part of the deliverable) against the running server: happy-path Register returned a
  real UUID + populated `CreatedAt` (GORM's auto-timestamp, confirmed non-zero); duplicate
  phone number → `AlreadyExists`; malformed phone → `InvalidArgument`; whitespace-only name
  → `InvalidArgument`. Same four outcomes as Entry 1, now through GORM, all observed
  directly from the RPC response.

### Known gaps / TODO for the next agent
- GORM's logger is fully silenced (`logger.Silent`). If per-query debug logging is ever
  needed (e.g. investigating a slow query), the honest fix is a small custom
  `logger.Interface` adapter that routes through the same `slog` JSON logger the rest of
  the service uses — not flipping `LogMode` back to `Info`/`Warn`, which would reintroduce
  the plain-text-to-stdout problem this entry just fixed.
- `userModel`'s column mapping relies on GORM's default snake_case `NamingStrategy`
  matching the existing migration's column names (`id`, `phone_number`, `full_name`,
  `created_at`) — verified true today, but there's no explicit `gorm:"column:..."` tag
  pinning it. If a future migration renames a column, GORM will silently look for the new
  default-mapped name; add explicit column tags at that point rather than relying on the
  convention continuing to line up.
- Same gaps as Entry 1 still apply and are unaffected by this change: no API Gateway, no
  login/PIN/session, no rate limiting, `buf.gen.yaml` still hardcoded to one output target.

### Do NOT do
- Do not re-enable GORM's default logger at `Info` or `Warn` level without routing it
  through `slog` first — it bypasses structured JSON logging and mislabels expected
  outcomes (like a duplicate-key conflict) as errors. See Verification for what that
  actually looked like.
- Do not add `AutoMigrate` calls anywhere in this service. Schema changes are new files
  under `migrations/`, applied by `internal/storage/postgres/migrate.go` — that boundary
  was deliberately preserved through this ORM swap, not an accident of what didn't get
  touched.
- Do not assume `errors.Is(err, gorm.ErrDuplicatedKey)` alone is being used for the
  duplicate-phone check — the repository still checks the specific constraint name via
  `*pgconn.PgError`, same precision as before GORM. `TranslateError: true` is enabled
  mainly so that unwrapping still works cleanly, not because the code switched to the
  generic sentinel.

## Entry 3 — Auto-load .env via joho/godotenv (fixes local `go run` failing on missing env vars)

- **time:** 21:53
- **agent:** Claude Sonnet 5 (Claude Code)
- **task:** User ran `go run cmd/server/main.go` locally and hit
  `USER_SERVICE_DATABASE_URL is required` because env vars weren't exported in their
  shell. User explicitly asked to use `github.com/joho/godotenv` to fix this.
- **status:** completed
- **scope:** apps/user-service
- **touches_money:** no

### What changed
- `go.mod` — added `github.com/joho/godotenv` (direct dependency). Explicit user request
  (§4.7 "state why" — the honest reason is the same as Entry 2: named library, not a
  technical requirement `os.Getenv` alone couldn't meet; flagging that rather than
  retrofitting a justification).
- `cmd/server/main.go` — `run()` now calls `godotenv.Load()` before `config.Load()`.
  A missing `.env` file is **not** treated as an error (checked via
  `errors.Is(err, fs.ErrNotExist)`) since that's the normal case in production/CI/Docker,
  where config comes from real environment variables, not a file. Any other error from
  `godotenv.Load()` (a `.env` file that exists but is malformed) still fails startup —
  that's a real local misconfiguration worth surfacing, not something to swallow.
  `godotenv.Load()` never overrides a variable already present in the real environment
  (documented behavior, verified below) — so this is strictly a local-dev convenience,
  never a way to override how the service is actually configured in a real deployment.
- **`.env` split into two, service-scoped vs. compose-scoped, instead of one shared root
  file** — `godotenv.Load()` with no arguments loads `.env` from the process's *working
  directory*, and the user runs the service from inside `apps/user-service/`. A single
  root `.env` would have needed a hardcoded relative path (`../../.env`) that breaks the
  moment the service is run from anywhere else (a different cwd, a container, `go build`
  output invoked from elsewhere). Instead:
  - `apps/user-service/.env.example` — new. `USER_SERVICE_DATABASE_URL`,
    `USER_SERVICE_GRPC_PORT` — the values `cmd/server/main.go` actually reads.
  - `.env.example` (root) — trimmed to just `USER_DB_*`, the values `docker-compose.yml`
    reads for the Postgres container. Added a comment pointing at the per-service file so
    the split doesn't read as an accident.
  - Created the real `apps/user-service/.env` locally (gitignored — confirmed via
    `git status --porcelain`, not just assumed from the `.gitignore` pattern) with the
    same values as before, so `go run ./cmd/server` (or `go run cmd/server/main.go`, as
    the user ran it) now works with zero exported env vars.

### Why
Straightforward fix for what the user hit. The two-file split is the one non-obvious
decision here — worth stating: it's driven by `godotenv.Load()`'s cwd-relative default
behavior, not a preference for more config files. If a second service is added later and
also wants `.env` auto-loading, the same pattern applies: that service gets its own
`.env`/`.env.example` in its own directory, not a shared one at the root.

### Invariants affected
None.

### Verification
- `go build ./...`, `go vet ./...`, `gofmt -l .` — all clean.
- `go test ./...` — unaffected, same results as Entry 2.
- Confirmed `apps/user-service/.env` is actually gitignored and both `.env.example` files
  are not: `git status --porcelain apps/user-service/.env apps/user-service/.env.example
  .env.example` → only the two `.env.example` files listed as `??` (untracked, stageable);

  `apps/user-service` with **no env vars exported** (the user's exact command) →
  `{"level":"INFO","msg":"migrations applied",...}` then `"grpc server listening"`,
  `"port":"50051"` — no `USER_SERVICE_DATABASE_URL is required` error.
- **Verified override precedence, not just presence**: re-ran with
  `USER_SERVICE_GRPC_PORT=50099` exported → server logged `"port":"50099"`, proving a real
  environment variable still wins over `.env`'s `50051`, matching godotenv's documented
  "will not override an existing env var" behavior — checked against actual behavior, not
  assumed from the doc comment alone.
- Killed both background server instances afterward; confirmed via `ps aux | grep
  cmd/server` that nothing was left running before finishing.

### Known gaps / TODO for the next agent
- If a `wallet-service`/`transaction-service`/etc. is added later, give it its own
  `.env`/`.env.example` pair in its own `apps/<service>/` directory following this same

  `docker-compose.yml`'s, not any individual service's.
- Same gaps as Entry 1/2 still apply and are unaffected by this change.

### Do NOT do
- Do not merge the two `.env.example` files back into one at the root "for simplicity" —
  that reintroduces the cwd-relative path problem this entry exists to avoid. If this

- Do not change `godotenv.Load()` to treat a missing `.env` as fatal — production and CI

    Body size capped at 1MiB via `http.MaxBytesReader` (boundary-input guard, §5.1).

    JSON *shape*, per architecture §4 ("validation of request shape" is the gateway's

### Why
**JSON field casing (camelCase, not snake_case):** no HTTP/JSON contract existed anywhere
in this repo before this entry — this was a real design choice, not a given. Chose
camelCase (`phoneNumber`, `fullName`) to match the frontend's existing TypeScript
conventions (`apps/web/features/transaction/types.ts` etc. are all camelCase) since the
frontend is this gateway's eventual consumer, over snake_case (which would mirror the
`.proto`/DB column naming instead). Nothing is wired to this contract yet, so this is
cheap to revisit if that's the wrong call — flagging it explicitly rather than treating it
as an obvious default.

**Route `POST /v1/auth/register`, not `/v1/users/register`:** the PRD groups Register under
"7.1 Authentication," and the architecture doc's suggested frontend structure has a
`features/auth/` directory — mirroring that grouping now leaves room for `/v1/auth/login`
next without a naming inconsistency.

**stdlib `net/http`, not a router library (chi/gin/echo):** Go 1.22+'s `http.ServeMux`
already supports `"POST /v1/auth/register"`-style method+path patterns, which is all one
route currently needs. Per §4.7, adding a router dependency for a single route isn't
justified yet — revisit if/when route count or matching complexity (path params, groups)
actually needs it.

**No rate limiting on `/v1/auth/register` in this pass**, despite this being exactly the
place Entry 1 said it belonged ("Needs to land with the API Gateway"). Rate limiting per
the architecture doc is Redis-backed, and adding Redis is a new infrastructure dependency
under §4.6 ("do not add... without the human explicitly asking") — the user asked for "the
api gateway," not "the api gateway plus Redis," so this is flagged as a known gap rather
than assumed in scope.

**Insecure gRPC transport** (gateway → user-service): matches the pattern already
established and tested in this repo (Entry 1's e2e verification client used the same
`insecure.NewCredentials()`). Fine for a local/private network; §19 requires TLS in
deployed environments — tracked below, not silently deferred.
