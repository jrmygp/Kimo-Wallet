### Naming decision
RPC name `GetUserByID`, and every Go method/interface/handler named after it (`UserService.GetUserByID`, `UserRepository.GetUserByID`, `UserServer.GetUserByID`, `UserHandler.GetUserByID`, `userServiceClient.GetUserByID`), were deliberately **kept as-is** even though the lookup key changed from the internal `id` to `kimo_id`. Renaming all of them (e.g. to `GetUserByKimoID`) would have touched more files for zero behavioral gain, and "GetUserByID" backed by an RPC still literally named `GetUserByID` in the wire contract stays self-consistent. Every layer's parameter got renamed to `kimoID`/`kimoId` instead, and a doc comment was added at each layer's definition saying explicitly "this looks up by KimoID, not the internal id, despite the name" — judged sufficient to prevent the confusion a bare rename would have fully eliminated. Purely internal names with no wire-contract tie (`domain.ErrInvalidKimoID`, `domain.NewGetUserByKimoIDInput`) *were* renamed, since nothing external depends on their old names.

### Why
The point of this feature is to stop exposing the internal UUID `id` as something a user types or shares — `kimo_id` is the public-facing handle instead (this is exactly what `apps/web`'s Transfer-sheet search UI, built 2026-08-28 Entry 2, already expected — its placeholder text has said "Search by KimoID..." since before this backend actually supported it). A UUID has 122 bits of keyspace, effectively collision-proof without any retry logic; a 12-character, 36-symbol KimoID has ~62 bits, still enormous for any realistic user count but not "never worth checking for" — hence the bounded retry loop in `Register`, a deliberately different design decision from `id` generation's "trust the space, don't check" for a keyspace that's meaningfully smaller. The migration's nullable-first-then-backfill-then-constrain shape is standard practice for adding a `NOT NULL UNIQUE` column to a table that may already have rows — the opposite order fails outright on the first pre-existing row.

### Invariants affected
Auth/contracts — no money. `GetUserByIDRequest.id` → `kimo_id` is a breaking wire-contract change (confirmed via `buf breaking`), judged acceptable here since both consumers of this contract (api-gateway, apps/web) live in this same monorepo and were updated in the same change — there is no external/versioned consumer of `user/v1` yet. Flagging this per docs/CLAUDE.md §4 rule 4 ("changing a published contract in a breaking way requires a new version directory") rather than silently deciding it doesn't apply: if this proto is ever consumed by something outside this repo, this decision should be revisited.
